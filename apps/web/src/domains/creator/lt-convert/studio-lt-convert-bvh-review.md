# LT 변환 three-mesh-bvh 가속 활용 검토 (2026-09-30)

`apps/web/src/domains/creator/studio-three-mesh-bvh-provider.ts`를 읽고,
LT 변환(`lt-convert`)에 BVH 가속을 붙이는 것이 타당한지 검토한 결론이다.
원칙: 무리한 구현 금지 — 정직하게 판단하고 문서로 남긴다.

## 결론

**1차 경로는 이미지 기반 Sobel 엣지 추출을 유지한다. BVH는 붙이지 않는다.**
소스 메시가 있을 때의 hidden-line(가려진 윤곽선) 제거 가속에만 의미가 있으며,
그것도 별도 티켓(향후 과제)으로 분리하는 것이 맞다.

## 판단 근거

### 이미지 기반 Sobel이 1차 경로로 적합한 이유

1. **LT 변환의 입력 정의 자체가 "합성된 최종 이미지"다.**
   CSP의 LT 변환은 3D 렌더 결과(조명·재질·배경 합성 포함)나 사진을 넣으면
   선화+톤으로 분리해 주는 기능이다. BVH는 기하 정보만 다루므로, 조명·재질·
   포스트이펙트가 반영된 최종 화면의 엣지를 만들 수 없다. 렌더 캡처와 사진
   모두에 동일하게 동작해야 한다는 티켓 요구와도 이미지 기반이 더 잘 맞는다.
2. **BVH 프로바이더의 연산자는 윤곽선 추출용이 아니다.**
   프로바이더가 제공하는 연산은 `raycastFirst`(광선 첫 충돌),
   `closestPoint`(최근접 표면), `shapeCandidates`/`lassoCandidates`(후보 삼각형
   집합)이다. "화면에 보이는 윤곽선"을 직접 뽑아내는 연산자는 없고, 만들려면
   실루엣 엣지 추출 + 투영 + 가림 판정을 새로 구현해야 한다.
3. **비용 대비 효과가 없다.**
   가림 판정을 픽셀 단위 `raycastFirst`로 하면 해상도에 비례해 수백만 회
   쿼리가 필요하고, 프로바이더의 쿼리당 예산(`maxTriangleTestsPerQuery`,
   동시 연산 4개 제한)과도 맞지 않는다.

### BVH가 의미 있는 지점 (향후 과제)

소스 메시(BufferGeometry)에 접근 가능하고, 뷰 행렬도 알 수 있는 경우에 한해
다음 하이브리드 방식이 가능하다. 단, 현재 티켓 범위를 넘으므로 구현하지 않는다.

1. 메시에서 기하학적 윤곽선(실루엣) 엣지를 추출한다.
2. 엣지를 화면에 투영한 뒤, 저해상도 오클루전 버퍼를 만든다.
   - 이때 각 버퍼 셀의 가림 여부는 BVH `raycastFirst`로 판정한다
     (픽셀 전수가 아니라 다운샘플된 그리드에서만).
3. 가려진 윤곽선 구간을 제거한 뒤, 이미지 기반 Sobel 결과와 합성한다.

이 방식은 "소스 메시 있음 + 사진 입력 없음"일 때만 성립한다. 사진 입력에는
기하 정보가 없어 BVH를 쓸 여지가 원천적으로 없다.

## 참고

- 프로바이더 예산 상수: `STUDIO_THREE_MESH_BVH_BUDGETS`
  (`maxTriangleTestsPerQuery: 250_000`, `maxConcurrentOperations: 4` 등).
- LT 엔진의 대용량 이미지 예산은 `STUDIO_LT_CONVERT_MAX_PIXELS`(1600만 px)로
  별도 관리한다. 두 예산은 서로 다른 자원(CPU 픽셀 연산 vs BVH 쿼리)을
  제한하므로 합치지 않는다.
