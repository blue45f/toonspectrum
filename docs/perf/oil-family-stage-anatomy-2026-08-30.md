# 유화 계열 라이브 획 — 단계별 해부와 남은 차단자

> 목표: "유화계열 등 긴 획이 길어질수록 급격히 느려지는 이슈를 근본적으로 해결"
> 제약: 브러시 품질을 낮추지 않는다.

`stroke-prefix-stability-2026-08-30.md` 는 대브 베드와 캐리어 기하·스테이션을 접두 안정하게
만들었다. 이 문서는 **출하 중인 `oil` / `acrylic` 프리셋**에서 이동당 비용이 실제로 어디에
있는지를 재고, 남은 부분이 왜 남았는지를 근거와 함께 적는다.

## 1. 왜 유화 계열만 유독 느린가

`studioOilRibbonProgramsForBrush` 를 덤프하면 갈린다:

| 브러시 | 프로그램 |
| --- | --- |
| `oil`, `acrylic` | `bristlePhysics` + `bristleLoadDynamics` + `impastoRelief` **전부 on** |
| `oil-impasto`, `oil-filbert`, `oil-flat`, `oil-round`, `gouache` | 없음 |

그리고 `StudioOilRibbonCarrierPlanner` 는 두 프로그램 중 **하나라도 켜져 있으면 런 재사용을
0 으로 내린다**(`reusableStations = dynamics || physics ? 0 : settledStations`). 즉 사용자가
"유화 계열"이라고 부르는 바로 그 두 프리셋이 접두 재사용을 전혀 못 받고 있었다. 프로그램이 없는
오일 변종들은 이미 재사용을 받고 있었고, 실제로 같은 대브 수에서 훨씬 쌌다.

## 2. 단계별 실측 (`oil`, 배치 플래너, 이 컨테이너)

`planStudioOilRibbonCarrier` 안에 임시 계측을 넣어 잰 값(ms/이동, 10회 평균):

| 단계 | 680 대브 | 2766 대브 | 4096 대브(캡) | 접두 재사용 가능? |
| --- | --- | --- | --- | --- |
| stations | 0.39 | 1.11 | 1.42 | ✅ 이미 재사용 중 |
| loadDynamics | 0.32 | 2.22 | 3.35 | ✅ **인과적 — 이번에 재사용** |
| bristlePhysics | 1.32 | 4.74 | 9.35 | ⚠️ `baseRadiusPx` 하나에 막힘 |
| impastoRelief | 5.09 | 5.76 | 8.40 | ❌ 전역 격자(거의 상수) |
| body | 0.23 | 0.36 | 1.63 | ❌ 닫힌 폴리곤 1개 |
| runBuild | 1.38 | 4.98 | 8.25 | ⚠️ 두 프로그램 접두가 안정해야 가능 |
| banding+weld+shells | 2.41 | 3.97 | 5.02 | ❌ 관측 min/max 스팬 = 설계상 전역 |
| **합계** | **11.2** | **23.2** | **37.6** | |

길이에 따라 **자라는** 항은 physics(9.35) + runBuild(8.25) + loadDynamics(3.35) = **20.95 ms,
캡에서 전체의 56%** 다. 나머지 ~15ms(banding + impasto + body)는 길이와 거의 무관한 바닥이다.

## 3. 이번에 고친 것 — 인과적 load dynamics

`planStudioOilBristleLoadDynamics` 는 **엄격하게 인과적인 전진 행진**이다: 스테이션 k 는
`pressures[k]`, `speeds[k]` 와 k−1 이 남긴 상태(`filmDrive`, `flattenDrive`, `speedEma`,
`laneReservoir[]`)만 읽고 앞을 보지 않는다. `stationCount` 는 배열 크기를 정할 뿐이다.

따라서 접두가 바이트 동일하면 출력 행 접두도 바이트 동일하다. 행진 루프를 `marchLoadDynamics`
커널로 뽑아 **배치 플래너와 증분 플래너가 같은 루프 하나를 공유**하게 했고(두 구현이 갈릴 수
없다), `StudioOilBristleLoadDynamicsPlanner` 가 정착 경계에서 상태를 스냅샷해 다음 프레임이 그
지점부터 이어 달린다.

재사용을 거부하는 조건(전부 테스트로 고정):

- **보관 상태는 정확히 `marched` 스테이션 뒤의 상태**이므로 그 지점에서만 이어 달릴 수 있다.
  획이 그보다 짧아지면 0 부터 다시 행진한다.
- `sampleSeries` 는 짧은 시리즈를 마지막 값으로 **고정(hold)** 한다. 그래서 이미 행진한
  스테이션이 획이 자라면서 다른 값을 읽게 되므로, 시리즈 길이가 스테이션 수와 정확히 같거나
  아예 없을 때만 재사용한다.
- laneCount / seed / initialLoad / depletionRate 가 움직이면 전량 재행진.

측정(이동당 캐리어 계획, `oil`, 성장하는 획을 실제로 걸으며 6회 중 최소/중앙):

| 표본 | 이전 | 이후 |
| --- | --- | --- |
| 1600 | 19.9 / 20.5 ms | 18.4 / 21.2 ms |
| 2000 | 24.2 / 27.2 ms | 22.9 / 25.0 ms |
| 2400 | 29.1 / 33.0 ms | 29.0 / 30.3 ms |

**정직하게: 1–3 ms 다.** 단계 비용(3.35ms)과 일치하며, 캡 근처에서는 대브 접두 자체가 무너져
남는 게 없다. 이것만으로 체감이 달라지지 않는다 — 아래 4절이 남은 본체다.

## 3-1. 병렬로 고친 것 — 털 시뮬의 스텝당 낭비 (픽셀 불변)

physics 단계는 전체를 다시 돌려야 하지만(4절), 스텝 하나의 비용은 줄일 수 있다.
`stepBristles` 는 이동당 4096번 불리는데 그 안에서:

- `capacityTotal` — 레이아웃은 생성 후 변하지 않으므로 **상수**인데 매 스텝 터프트 전체를 다시
  더하고 있었다. 생성 시 같은 순서로 한 번 더해 상태에 두었다(같은 순서 → 비트 동일).
- 모세관 재분배가 `new Float64Array(count - 1)` 를 **매 스텝 할당**했다. 읽히기 전에 전부
  덮어쓰는 값이라 상태가 소유하는 스크래치로 옮겼다 — 프레임당 4096번의 할당이 사라진다.

## 4. 남은 차단자 — `baseRadiusPx` 하나

`planBristlePhysics` 도 **인과적 전진 행진**이다. 스테이션 루프는 `stationXs[k]`,
`stationYs[k]`, `pressures[k]` 와 터프트 상태만 읽는다. 전역 입력은 정확히 하나:

```ts
baseRadiusPx: meanBy(stations, (station) => station.radiusY)
```

이 값은 (1) `createPhysicsTuft` 를 통해 터프트의 정지 배치 전체, (2) `restBristleRadiusPx`,
(3) 레인 오프셋 정규화에 들어간다. 즉 **획이 자랄 때마다 이미 그려진 부분의 시뮬이 통째로
정당하게 달라진다.**

실측(획을 걸으며 `oil`):

- 획 전체에 걸친 **총 변동 18.2%** (8.56 → 10.12 px)
- 프레임당 스텝은 3200 표본에서도 0.05–0.07% 로 **수렴하지 않고 계속 움직인다**

이것이 `reusableStations = 0` 의 유일한 이유다. 이 값을 획 길이와 무관하게 만들면
physics(9.35) + runBuild(8.25) = **캡에서 17.6 ms/이동**이 접두 재사용 대상이 되고, 자라는 항이
평평해진다. 하지만 그건 `oil` / `acrylic` 로 그린 **모든 획의 최종 픽셀이 바뀐다**는 뜻이다.

**결정: 하지 않는다.** 최종 픽셀은 바뀌지 않아야 한다는 것이 이 작업의 제약이다. 따라서 이
17.6 ms 는 열지 않고 남겨 두며, 성능 작업은 출력이 바이트 동일한 범위 안에서만 한다. 되돌리려면
이 절이 재개 조건 그대로다.

부수적으로 이 전역성은 성능과 무관한 아티팩트이기도 하다: 획을 계속 그으면 **이미 칠해진 털의
가로 오프셋과 폭이 18% 범위에서 계속 흔들린다.**

## 5. 칠(paint) 단계를 증분화하려던 시도 — 측정으로 기각

이동당 칠 비용은 JS 경로 추적 0.7–5.7 ms(+ 래스터화)다. 더티 사각형 재칠을 구현했다:
바뀐 사각형만 지우고 그 안에 걸치는 런만 같은 순서로 다시 그리면(레인당 한 번의 `stroke()` 규칙
유지) 전체 재칠과 픽셀 동일하다 — 단, **플랜의 "칠 정체성"(레인 수·레인별 lineWidth/opacity/
loadBand·bodyOpacity)이 그대로일 때만** 성립한다.

성장하는 획 599 프레임에서 그 정체성이 유지된 프레임: **0 건 (0.0%)**.

- `lineWidth` 가 500 프레임 중 488 에서 변함
- `bodyOpacity` 는 `meanStationOpacity` — 획 전역 평균이라 431 프레임에서 변함
- 레인 opacity 는 밴드 평균, 밴드 경계는 관측 min/max 로드 스팬 — 역시 전역

즉 칠 단계가 O(N)/프레임인 것은 낭비가 아니라 **플랜의 색조가 획 전체의 함수라서**다. 이 조건이
바뀌지 않는 한 더티 사각형 코드는 절대 타지 않는 죽은 코드이므로 트리에 넣지 않았다(패치는
보관). 4절의 전역성과 같은 뿌리이며, 그쪽이 먼저 정리돼야 여기도 열린다.

## 6. 재개 조건 요약

| 항목 | 이득(캡 기준) | 재개 조건 |
| --- | --- | --- |
| physics + runBuild 접두 재사용 | ~17.6 ms/이동 | `baseRadiusPx` 를 획 길이와 무관하게 — **픽셀이 바뀌므로 보류** |
| 더티 사각형 재칠 | 칠 O(N)→O(꼬리) | 위와 더불어 밴딩/bodyOpacity 의 전역성 정리 |
| impastoRelief | ~5–8 ms/이동 | 거의 상수. 길이 의존 문제가 아니라 별건 |
