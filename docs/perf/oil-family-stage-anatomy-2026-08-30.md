# 유화 계열 라이브 획 — 단계별 해부와 근본 원인

> 목표: "유화계열 등 긴 획이 길어질수록 급격히 느려지는 이슈를 근본적으로 해결"
> 제약: 브러시 품질을 낮추지 않는다. `oil` / `acrylic` 의 최종 픽셀은 바뀌지 않는다.

`stroke-prefix-stability-2026-08-30.md` 가 대브 베드와 캐리어 기하·스테이션을 접두 안정하게
만들었다. 이 문서는 **출하 중인 `oil` / `acrylic`** 에서 이동당 비용이 실제로 어디에 있는지를
재고, 남아 있던 차단자가 사실은 **잘못된 전제 하나**였음을 보인다.

## 1. 왜 유화 계열만 유독 느렸나

`studioOilRibbonProgramsForBrush` 를 덤프하면 갈린다:

| 브러시 | 프로그램 |
| --- | --- |
| `oil`, `acrylic`, `fluid-paint*` | `bristlePhysics` + `bristleLoadDynamics` + `impastoRelief` **전부 on** |
| `oil-impasto`, `oil-filbert`, `oil-flat`, `oil-round`, `gouache` | 없음 |

그리고 캐리어 플래너는 두 프로그램 중 하나라도 켜져 있으면 런 재사용을 0 으로 내렸다
(`reusableStations = dynamics || physics ? 0 : settledStations`). 즉 사용자가 "유화 계열"이라
부르는 **바로 그 프리셋들만** 접두 재사용을 전혀 못 받고 있었다.

## 2. 단계별 실측 (`oil`, 배치 플래너, 이 컨테이너)

`planStudioOilRibbonCarrier` 에 임시 계측을 넣어 잰 값(ms/이동, 10회 평균):

| 단계 | 680 대브 | 2766 대브 | 4096 대브(캡) |
| --- | --- | --- | --- |
| stations | 0.39 | 1.11 | 1.42 |
| loadDynamics | 0.32 | 2.22 | 3.35 |
| bristlePhysics | 1.32 | 4.74 | 9.35 |
| impastoRelief | 5.09 | 5.76 | 8.40 |
| body | 0.23 | 0.36 | 1.63 |
| runBuild | 1.38 | 4.98 | 8.25 |
| banding+weld+shells | 2.41 | 3.97 | 5.02 |
| **합계** | **11.2** | **23.2** | **37.6** |

길이에 따라 **자라는** 항은 physics + runBuild + loadDynamics = 캡에서 **20.95 ms (전체의 56%)**.
나머지 ~15 ms(banding + impasto + body)는 길이와 거의 무관한 바닥이다.

## 3. load dynamics — 인과적이므로 이어 달린다

`planStudioOilBristleLoadDynamics` 는 **엄격하게 인과적인 전진 행진**이다. 스테이션 k 는
`pressures[k]`, `speeds[k]` 와 k−1 이 남긴 상태(`filmDrive`, `flattenDrive`, `speedEma`,
`laneReservoir[]`)만 읽고 앞을 보지 않는다. `stationCount` 는 배열 크기를 정할 뿐이다.

행진 루프를 `marchLoadDynamics` 커널로 뽑아 **배치와 증분이 같은 루프 하나를 공유**하게 했고,
`StudioOilBristleLoadDynamicsPlanner` 가 정착 경계에서 상태를 스냅샷해 다음 프레임이 그 지점부터
이어 달린다. 재사용을 거부하는 조건(전부 테스트로 고정):

- 보관 상태는 **정확히 `marched` 스테이션 뒤의 상태**이므로 그 지점에서만 이어 달릴 수 있다.
  획이 그보다 짧아지면 0 부터 다시 행진한다.
- `sampleSeries` 는 짧은 시리즈를 마지막 값으로 **고정(hold)** 하므로, 이미 행진한 스테이션이
  획이 자라며 다른 값을 읽게 된다 → 시리즈 길이가 스테이션 수 이상이거나 없을 때만 재사용.
- laneCount / seed / initialLoad / depletionRate 가 움직이면 전량 재행진.

## 4. 근본 원인 — `baseRadiusPx` 는 애초에 나눠서 사라진다

`planBristlePhysics` 도 인과적 전진 행진이다. 스테이션 루프는 `stationXs[k]`, `stationYs[k]`,
`pressures[k]` 와 터프트 상태만 읽는다. 전역 입력은 정확히 하나였다:

```ts
baseRadiusPx: meanBy(stations, (station) => station.radiusY)   // 획 전역 평균
```

주석은 이 값이 "움직이니 시뮬 전체가 정당하게 달라진다"고 적어 두었고, 그 한 줄이 유화 계열의
접두 재사용을 통째로 막고 있었다. 실제로 이 값은 획 전체에서 **18.2% 변동**하고 3200 표본에서도
프레임당 0.05–0.07% 씩 계속 움직인다(수렴하지 않는다).

**그런데 그럴 필요가 없었다.** 이 프로그램이 내보내는 모든 스트림은 앵커를 **다시 나눠 없앤다**:

- `laneOffsetRatio = lateral / baseRadiusPx`. `lateral` 은
  `restOffset·radius·splay + splitDrive·splitAmplitude·radius·clumpDirection` 이고 틸트 시프트
  항까지 전부 `radius` 를 인수로 갖는다 → 나누면 사라진다.
- `laneWidthScale = contactRadius / restBristleRadiusPx`. `contactRadius` 는 `bristleRadiusPx`
  를 인수로 갖는데 그게 곧 `restBristleRadiusPx` 다 → 사라진다.
- `laneLoadMultiplier` · `spread` · `splitDrive` · `inkRatio` 는 반경을 아예 읽지 않는다.

즉 주석의 전제가 **사실이 아니었다**.

### 4-1. 그래서 앵커를 얼린다 (`settled-prefix-v2`, 기본값)

상쇄에 기대어 재사용을 켜는 것은 대수적으로는 맞아도 **부동소수 결합 순서에 기대는** 셈이라
적절치 않다. 대신 앵커를 앞 `STUDIO_OIL_PHYSICS_REST_RADIUS_ANCHOR_STATIONS`(256) 스테이션
평균으로 **고정**해 행진을 **정확히 인과적**으로 만든다. 접두는 상쇄가 성립해서가 아니라
**구성상** 정착한다.

물리적으로도 이쪽이 맞다 — 터프트의 정지 폭은 브러시와 그 위의 필압이 정하는 성질이지, 획을
얼마나 더 그었는지의 함수가 아니다. `stroke-mean-v1` 은 명시적 옵트아웃으로 남겨 두었다.

측정은 **한 프로세스 안에서 두 앵커를 라운드마다 번갈아** 돌리고 각 지점의 최소를 취했다
(이 컨테이너는 프로세스 간 편차가 커서 별도 실행 비교는 신뢰할 수 없다):

| 이동당 캐리어 계획 (best-of-5) | `oil` 이전 → 이후 | `acrylic` 이전 → 이후 |
| --- | --- | --- |
| 400 표본 | 7.94 → **5.75 ms** (−28%) | 7.48 → **5.36 ms** (−28%) |
| 800 | 10.11 → **6.15 ms** (−39%) | 10.49 → **7.20 ms** (−31%) |
| 1200 | 13.51 → **7.45 ms** (−45%) | 12.73 → **7.54 ms** (−41%) |
| 1600 | 17.36 → **9.86 ms** (−43%) | 17.79 → **9.61 ms** (−46%) |
| 2000 | 24.39 → **11.61 ms** (−52%) | 22.07 → **12.31 ms** (−44%) |
| 2400 (대브 캡) | 29.64 → 30.20 ms | 29.70 → 28.98 ms |

재사용된 런: 2000 표본에서 0 → **21,824**.

**길이가 자랄수록 벌어지던 항이 사라졌다.** 400→2000 표본에서 이전은 7.9→24.4 ms (3.1배),
이후는 5.8→11.6 ms (2.0배)다. 캡(2400)에서 재사용이 0 으로 돌아가고 이득이 사라지는 것은
설계대로다 — `sampleStations` 가 격자를 전면 재적합하므로 어떤 접두도 살아남지 않는다(별건).

### 4-2. 그리고 시뮬 자체도 이어 달린다

앵커가 얼면 physics 행진도 **정확히 인과적**이므로, load dynamics 와 같은 처리를 할 수 있다.
행진 루프를 `marchPhysicsOil` 커널로 뽑아 배치·증분이 공유하게 하고,
`StudioBristlePhysicsOilPlanner` 가 정착 경계에서 터프트를 스냅샷해 다음 프레임이 이어 달린다.

스냅샷 대상(`BristleBrushCarry`)은 스텝을 가로지르는 것만이다 — 잉크 배열과 스칼라 상태, 그리고
캐리어 쪽의 hold-last 레인 기하(`heldOffset`/`heldWidth`). `contactX/Y/Radius/Alpha` 는 매 스텝
모든 털에 대해 **읽히기 전에 전부 쓰이므로** 경계를 넘지 않고, `layout`/`config`/`clumpDirection`
은 생성 시 고정이라 복사하지 않는다.

**이로써 "이미 그려진 부분의 털 시뮬을 매 프레임 통째로 다시 돌린다"가 사라졌다.**

### 4-3. 병렬로 고친 것 — 털 시뮬 스텝당 낭비

`stepBristles` 는 이동당 4096번 불린다. 그 안에서:

- `capacityTotal` — 레이아웃은 생성 후 변하지 않으므로 **상수**인데 매 스텝 터프트 전체를 다시
  더하고 있었다. 생성 시 같은 순서로 한 번 더해 상태에 둔다.
- 모세관 재분배가 `new Float64Array(count - 1)` 를 **매 스텝 할당**했다. 읽히기 전에 전부
  덮어쓰는 값이라 상태가 소유하는 스크래치로 옮겼다.

## 5. 기존 엔진 검토

리포지토리에는 이미 상용 오픈 엔진 평가 카탈로그가 커밋돼 있다
(`studio-commercial-open-engine-evaluation.ts`, 12개 엔진). `paint-oil` 을 제공하는 항목:

| 엔진 | 라이선스 | 판정 |
| --- | --- | --- |
| **Hokusai** (`packages/studio-hokusai-wasm`) | MIT OR Apache-2.0 | `primary-pin-candidate`. **이미 vendoring 돼 있고** `beginStroke / addSample / dirtyBounds / dirtyFrame` 라는 **완전 증분 API** 를 갖는다 |
| libmypaint / MyPaint | ISC | 수치는 이미 `STUDIO_OSS_OIL_FILM_RECIPE` 로 들어와 있음 |
| Krita (colorsmudge/hairy 등) | GPL-2.0+ | `copyleft-isolate` — 클린룸 재구현만 가능 |
| Mixbox | CC BY-NC | `non-commercial-block` |
| Clip Studio / Rebelle | 독점 | `closed-reference-only` |

즉 **Hokusai 가 정답 후보이고 라이브 워커까지 이미 배선돼 있다**
(`studio-hokusai-live-brush.worker.ts`). 다만 `resolveStudioHokusaiProductLiveAdmission` 이
막고 있고 `STUDIO_HOKUSAI_PRODUCT_PROMOTED_PRESETS` 는 **빈 배열**이다 — 정책 주석대로
"committed full-size comparison does not pass visual parity or the 1.2x throughput gate".

따라서 유화를 Hokusai 로 갈아타는 것은 성능 수정이 아니라 **프리셋별 품질 승격 리시트를 만드는
제품 결정**이고, 기존 게이트가 그 절차를 이미 정의해 두었다. 이번에는 그 게이트를 우회하지 않고
현재 캐리어의 알고리즘을 고쳤다(4절). Hokusai 전환을 원하면 그 게이트가 요구하는 것은 프리셋별
시각 패리티 + 1.2x 처리량 리시트다.

## 6. 칠(paint) 단계를 증분화하려던 시도 — 측정으로 기각

이동당 칠 비용은 JS 경로 추적 0.7–5.7 ms(+ 래스터화)다. 더티 사각형 재칠을 구현했다: 바뀐
사각형만 지우고 그 안에 걸치는 런만 같은 순서로 다시 그리면(레인당 한 번의 `stroke()` 규칙 유지)
전체 재칠과 픽셀 동일하다 — 단 **플랜의 "칠 정체성"(레인 수·레인별 lineWidth/opacity/loadBand·
bodyOpacity)이 그대로일 때만** 성립한다.

성장하는 획 599 프레임에서 그 정체성이 유지된 프레임: **0 건 (0.0%)**.

- `lineWidth` 가 500 프레임 중 488 에서 변함
- `bodyOpacity` 는 `meanStationOpacity` — 획 전역 평균이라 431 프레임에서 변함
- 레인 opacity 는 밴드 평균, 밴드 경계는 관측 min/max 로드 스팬 — 역시 전역

즉 칠이 O(N)/프레임인 것은 낭비가 아니라 **플랜의 색조가 획 전체의 함수라서**다. 절대 타지 않을
죽은 코드이므로 트리에 넣지 않았다. 4절과 달리 이쪽 전역성은 실제로 그림을 정하므로, 열려면
밴딩/`bodyOpacity` 의 색조 모델 자체를 바꿔야 한다 — 그건 픽셀이 바뀌는 결정이다.

## 7. 픽셀 불변 검증

- **플랜 비교 70건 전부 동일**: `oil`/`acrylic` × 획 모양 5종 × 길이 7종(대브 캡까지), 그리고
  틸트를 준 베드 1건에서 `settled-prefix-v2` 와 `stroke-mean-v1` 의 플랜이 바이트 동일.
- **CanvasKit 실제 래스터화 대조**: `oil`/`acrylic` × 모양 3종 × 길이 2종에서
  **maxDelta 0/255, meanDelta 0.000**.
- **`main` 대비 다이제스트** (배치 5길이 + 증분 플래너 70프레임을 이어붙인 SHA-256) 가 6개
  프리셋 전부 동일 — 앵커 고정, 런 재사용, load dynamics 재개, physics 재개, 털 모델 스텝
  정리를 **모두 적용한 상태에서**:

```
oil                    d1a2b494136c098ee158fdb518d9eb78
acrylic                c1d9662cace925308982e194635bf437
oil--filbert-ribbon    daf6c900a76a9c2cfff0ca8d6e00a341
oil--impasto-ribbon    18b6eeec67f330491859f3ec6f2da3a9
oil-impasto            3aa349662d6ad1a7b0228c1934cc6d71
gouache                3aa349662d6ad1a7b0228c1934cc6d71
```

- 앵커 창(256 스테이션)에 못 미치는 짧은 획은 v1 과 **같은 값을 같은 순서로** 더하므로 정의상
  비트 동일하다.

## 8. 대브 캡 — 재적합 자체를 6배 싸게 (픽셀 불변)

캡(4096 대브)에서는 `sampleStations` 가 전체 호에 격자를 다시 깔기 때문에 어떤 접두도 살아남지
않는다. 그 전면 재구성이 이동당 28–30 ms 였다. **격자를 바꾸지 않고**(= 픽셀을 바꾸지 않고)
그 재구성 비용만 줄였다.

`appendOilBrushDabs` 의 안쪽 루프는 (스테이션 × 털)마다 도는데, 캡에서 약 90k 회다. 그 안에서
**스테이션과 무관한 값들을 매번 다시 계산**하고 있었다:

| 값 | 실제 의존성 | 캡에서의 계산 횟수 → 서로 다른 값의 수 |
| --- | --- | --- |
| `pitch` | 털·시드 | 90k → 22 |
| `hairGauge` (`** 1.4`) | 털·시드 | 90k → 22 |
| `reservoir` (`** 1.9`) | 털·시드 | 90k → 22 |
| load `start`/`end` 해시 | 노트(=103 스테이션마다) · 털 | 180k → ~0.9k |
| drift `start`/`end` 해시 | 노트(=162 스테이션마다) · 털 | 180k → ~0.6k |
| `contactWidth`, 건조 바닥항 | 스테이션 | 90k → 4096 |

털별 상수는 베드당 한 번 표로 만들고, 노트 해시는 노트 인덱스가 움직일 때만 다시 채운다
(스테이션 walk 를 따라 노트는 단조 증가한다). 스테이션 단위 항은 털 루프 밖으로 뺐고,
`bristleOffsets.map(...)` 의 스테이션마다 새로 만들던 클로저·배열도 없앴다.

**연산 순서는 그대로 두었다** — 예를 들어 `radiusXRatio` 의 `0.62 + tooth*0.28 + pressureFeel*0.08`
은 결합 순서상 압력항을 따로 묶을 수 없어 그대로 두었고, `radiusYRatio` 의 두 스케일도 하나로
곱해두지 않고 원래 순서대로 두 번 곱한다.

| | main | 이 브랜치 |
| --- | --- | --- |
| `planOilBrushDabs` 800 표본(1386 대브) | 9.9 ms | **3.0 ms** |
| 1600 표본(2766 대브) | 17.2 ms | **2.3 ms** |
| 2200 표본(3820 대브) | 28.3 ms | **4.6 ms** |
| **캡 4096 대브 (2600–6000 표본)** | **28.0–29.3 ms** | **3.8–5.0 ms** |

캡 이하 구간에서는 증분 플래너가 이미 대브를 거의 전부 재사용하므로(0.3 ms) 체감이 없지만,
이 경로는 **커밋·정착·SVG 내보내기·비초안 렌더가 쓰는 배치 플래너**이기도 해서 그쪽이 함께 빨라진다.

이동당 전체(대브+캐리어)는 캡 이하에서 **7–11 ms** 로 60 Hz 예산 안에 들어왔다. 캡에서는 캐리어
전면 재계획(~30 ms)이 남아 지배적이다.

### 8-1. 픽셀 불변 검증

베드 948개 — 브러시 6종(`oil`·`acrylic`·`oil--filbert-ribbon`·`oil--impasto-ribbon`·`gouache`·
`oil-flat`) × 획 모양 4종 × 길이 9종(1·2·40·300·900·1800·2600·3400·5000 표본, 캡 양쪽) ×
굵기 3종, 그리고 증분 플래너로 성장하는 획을 300프레임 걸은 결과를 이어붙인 SHA-256 이
`main` 과 **완전히 동일**: `e581b0e92147cbe53c1432ecd9367175a0d93cdd6f0d3e8cf14d2953643dde1d`

## 8-2. 캡 이후 라이브 프리뷰가 얼어 있던 문제

캡 최적화를 재다가 발견한 것. 오버레이는 `paintedDabs === dabs.length` 로 "바뀐 게 없다"를
판정했는데, **이 카운트는 캡에서 4096 에 고정된다**. 그리고 캡은 카운트가 근거이기를 멈추는 바로
그 지점이다 — `sampleStations` 가 전체 호에 격자를 다시 깔기 때문이다.

특히 캡 분기는 마지막 스테이션을 **마지막 소스 점 그대로** 넣는다:

```ts
if (stationIndex === stationLimit - 1) { stations.push(points.at(-1)!); continue; }
```

즉 캡에서도 획의 끝은 커서에 정확히 붙어 있어야 하는데, 칠하기를 멈추면 **끝점이 그 자리에
얼어붙어 커서와 눈에 띄게 분리된다.** 4096 대브를 넘어선 오일 획은 드래그가 끝날 때까지 그랬다.
`appendFrom` 의 반환 상태도 같은 포화 카운터로 계산돼 실제로 칠한 프레임을 `noop` 으로 보고했다.

### 왜 고정 스트라이드로는 안 되는가

처음에는 "캡 베드는 재분배되니 표본 하나의 이동은 서브픽셀"이라고 보고 32 표본마다 합쳐 칠하려
했다. **내부 스테이션에만 맞고 끝점에는 틀린 전제였다**(위 코드). 끝이 얼마나 뒤처지는지는
커서 속도와 이 기기의 재계획 비용이 정하는데, 상수는 둘 다 모른다 — 3 px/표본이면 32 표본은
~93 px, 120–240 Hz 입력에서 130–260 ms 다.

### 그래서: 재계획 비용 자신을 예산으로 쓴다

`t` 만큼 걸린 캡 재칠은 다음 재칠을 `t · (DIVISOR − 1)` 만큼 미룬다
(`OIL_CAP_REPAINT_DUTY_DIVISOR` = 3). 베드는 어떤 기기에서도 포인터 시간의 **1/3 을 넘게 쓰지
않고**, 빠른 기기는 자주 칠해 커서에 붙어 있고 느린 기기는 덜 칠하되 여전히 따라간다. 상수가
기기를 짐작하지 않는다.

함께 정리한 것:

- 가드가 대브 카운트 대신 **계획 입력 자체**(점 배열과 필압)를 비교한다. 값싼 지문으로는 안 된다 —
  표본 수만 세면 같은 길이의 authoritative 초안이 예측을 **대체**한 경우를 못 보고, 끝점을 더해도
  **내부만 교정된** 경우를 놓친다. 둘 다 회수된 예측 픽셀을 화면에 남긴다. 길이를 먼저 보므로
  자라는 경우(대부분)는 비교 한 번이고, 전량 스캔은 길이가 같을 때만 도는데 그 대상은 수십 ms
  짜리 계획이다.
- 가드가 **계획 전에** 돈다 — 기존에는 계획한 뒤 버렸다.
- 포인터 업은 유예된 꼬리를 반드시 흘려보내되(`finalize`), 이미 일치하는 베드를 공짜로 다시
  세우지는 않는다.
- 반환 상태가 실제 칠 횟수(`paintedOilPasses`)를 읽어 `noop` 오보가 사라졌다. 단 이 카운터는
  **따로** 본다 — `paintedDabs` 는 예측 꼬리가 회수되면 수천씩 **줄어들 수 있어**, 합치면 그 하락이
  실제 재칠의 `+1` 을 삼켜 화면을 지우고 다시 칠한 프레임이 `noop` 으로 보고된다.
- **계획 뒤의 두 번째 판정은 없앴다.** 예전에는 새 계획의 대브 수가 칠한 것과 같으면 조기 반환했는데,
  그 수는 근거가 아니다 — 캡에서 포화하는 데다 캡 아래에서도 마찬가지로 눈이 멀어서, 점은 그대로 두고
  **필압만 교정한** 초안은 스테이션이 전부 유지돼 수가 같은데 대브는 다르다. 계획을 세워 놓고 버리니
  회수된 픽셀이 남았다. 위의 입력 비교가 이미, 그것도 계획 **전에** 답을 주므로 이 검사는 더 약한
  중복이었다. 캡 아래에서 커서가 느려 스테이션 간격을 못 넘긴 프레임들이 이제 칠해진다 — 원래 정지의
  더 작은 판이었다.
- **없는 시리즈는 없는 것끼리 같다.** 마우스 입력은 `pressures` 가 아예 없는데(`undefined`),
  없는 것을 "무엇과도 다르다"로 보면 그런 획은 이 검사를 영영 통과하지 못한다 — 카운트 검사가
  꺼져 있는 캡에서 아무것도 바뀌지 않은 append 마다 4096 대브를 다시 칠하고, 깨우기가 한 번 더
  칠한다.

**캡 아래 동작은 그대로다** — 계획 입력이 달라지면 칠한다.

유예 판정은 **점 복사보다 먼저** 한다. 유예 여부는 카운터 하나와 타임스탬프 둘로 정해지는데,
`flatFinitePoints` 는 누적된 점 이력 전체를 훑어 복사한다. 곧 버릴 이벤트를 위해 그걸 복사하면 캡
이후 모든 포인터 프레임에 O(N) 할당이 붙어 드래그 전체로 2차가 되고, 하필 이 가드가 지키려는 예산
**바깥**에서 그렇게 된다.

유예에는 **깨우기가 따라붙는다**. 유예는 새 끝점을 담은 유일한 이벤트를 버리는 것이라, 그 뒤로
사용자가 손을 멈추면 다시 물어볼 사람이 없어 프리뷰가 **멈춰 있는 커서에서 떨어진 채로** 남는다 —
원래 정지의 축소판이다. 그래서 유예할 때 남은 쿨다운만큼의 깨우기를 예약하고, 획이 끝나거나
버려지면 취소한다.

쿨다운은 재칠이 **끝난 시각**부터 잰다. 시작 시각부터 재면 칠에 쓴 시간을 그대로 돌려주게 되어
실제 점유율이 1/3 이 아니라 1/2 이 된다. 리사이즈로 `replay()` 가 캡 재칠을 한 경우 그 비용도
활성 상태로 되돌려 준다 — 안 그러면 리사이즈 직후 공짜 재구성이 한 번 생긴다.

겸사겸사 잡은 것: `extendOilRadiusMean` 이 누적합을 다시 심을 때 **이전의 더 긴** 칠한 개수까지
돌면서 **새로운 더 짧은** 배열을 읽어 배열 밖을 참조하고 던졌다. 회수로 베드가 줄면 바로 걸린다.
이건 이 브랜치가 만든 게 아니다 — PR 기준점의 코드와 바이트 단위로 같고, 캡 아래 회수는 이미
걸리고 있었다. 이제 배열이 실제로 가진 만큼으로 자른다(줄어든 경우엔 짧은 배열 전체를 더하게 되는데,
이는 전체 reduce 와 같은 좌→우 순서라 값이 비트 단위로 같다).

열 성질을 각각 반증적으로 고정했다(해당 부분만 되돌리면 그 테스트만 적색): 캡을 넘긴 획이
자라면 다시 칠한다 / 비싼 재칠은 비례해서 유예된다 / 쿨다운은 끝난 시각부터다 / 유예하면 스스로
깨어나 칠한다 / 같은 길이의 대체 초안도, 내부만 교정된 초안도 다시 칠한다 / 이미 일치하는
베드는 `end()` 에서 다시 세우지 않는다 / 새 표본이 없는 append 는, `pressures` 가 없는 획에서도
건너뛴다 / 줄어든 베드의 재칠은 `noop` 이 아니라 `appended` 다 / 유예되는 append 는 점 이력을
읽지 않는다 / 대브 수가 같은 캡 아래 교정도 다시 칠한다. 예산의 타이밍과 깨우기는 **주입한 시계·타이머**로 검증해 기기 속도나 실제 타이머에
좌우되지 않는다.

## 10. 캡 격자를 접두 안정으로 (픽셀 변경 승인 후)

§9 의 첫 줄을 실제로 걷어낸 기록. **오일 계열 한정**이다.

### 무엇이 문제였나

`sampleStations` 의 캡 분기는 예산을 "호 전체에 정확히 `stationLimit` 개를 균등 배치"로 지켰다:

```ts
const targetDistance = totalLength * (stationIndex / (stationLimit - 1));
```

`totalLength` 가 모든 스테이션 위치에 들어간다. 호가 자라면 **전부 이동**한다. 그래서 캡 이후
성장하는 획은 이전 계획과 공유하는 접두가 없고, 그 위에 얹힌 것 — 대브 베드, 평활 지오메트리,
스테이션, 털 런, 레인 — 이 이동마다 처음부터 다시 만들어졌다.

### 무엇으로 바꿨나

예산을 **간격을 굵히는 쪽**으로 지킨다. 간격은 `totalLength` 에 의존하지 않는 고정 사다리에서
고르므로, 이미 놓인 스테이션은 호가 자라도 그 자리에 있고 새 스테이션만 뒤에 붙는다. 간격이
바뀌는 것은 호가 사다리 한 칸을 넘을 때뿐이고, 이는 획 길이에 **로그**다.

사다리 비율은 `2^(1/4) ≈ 1.19`. 한 칸을 오르는 순간이 유일하게 전량 재계산이 필요한 시점이라
굵은 비율은 재계산 횟수를 줄이고 고운 비율은 밀도를 예산에 붙인다. 1.19 는 밀도 손실을 한 자릿수
퍼센트대로 누르면서 재계산을 로그로 유지한다.

### 측정 (컨테이너, 4096 대브 베드, 이동당)

| | main | 사다리 |
| --- | --- | --- |
| 대브 계획 | 8.6 ms | **2.5 ms** |
| 캐리어 계획 | 69.3 ms | **33.3 ms** |
| 합계 | 77.9 ms | **35.8 ms** (−54%) |

캐리어 내부를 쪼개 보면 격자가 무엇을 풀었는지가 분명하다 — 털 런 빌드가 **70.9 ms → 1.9 ms**
(재사용 19878/20065 런). 지오메트리·스테이션도 0.5 ms 이하로 내려온다.

### 픽셀은 어떻게 바뀌나

캡 아래는 **바이트 단위로 동일**하다. 4 종 획 모양 × 2 브러시 × 6 길이 × 3 굵기 = 144 베드를
계획해 대브 배열 다이제스트를 비교한 결과, 달라진 44 개는 **전부 캡 베드**였고 캡 아래 100 개는
전부 일치했다.

캡 베드의 대브 수는 4096 → **3492~4090 (밀도 85~100%)**. 사다리가 한 칸 오른 직후가 가장 성기고
(1/1.19 = 84%) 다음 칸까지 자라며 100% 로 회복하는 톱니라, 어디를 재느냐로 값이 갈린다. 오일
대브는 반경이 간격의 몇 배라 겹침이 크고, 이 정도 변화는 텍스처의 알갱이를 조금 굵게 만든다.

### 오일에만 적용한 이유

`sampleStations` 는 글리터·파스텔도 쓰고, **`planOilBrushDabs` 자체를 에어브러시 계열 SVG
익스포트가 쓴다**(256/512 예산). 그쪽은 캐리어 파이프라인이 없어 재계산이 아프지 않으니 이득 없이
분포만 바꿀 이유가 없다.

그래서 모드를 `FxOilPlanInput.capMode` 로 올려 **호출부가 고른다**. 기본은 기존 refit 이고, 사다리를
켜는 곳은 오일을 계획하는 두 곳뿐이다 — 라이브 오버레이와 SVG 익스포트의 oil 분기. 같은 획을
계획하는 모든 경로가 같은 값을 넘겨야 한다는 점을 타입 주석에 못박았다: 안 그러면 한 획이 미리보기와
익스포트에서 다른 분포로 나온다.

검증(깨끗한 워크트리 대 현재 브랜치): 에어브러시 24/24 바이트 동일, 오일 캡 아래 100/100 동일.

### 최소 예산에서 끝점이 잘리던 것

사다리는 예산에서 **양 끝점을 모두** 예약해야 한다. 내부 예산을 1 로 바닥 처리했더니
`maxDabs: 2`(지원되는 최소값)에서 내부 스테이션 하나가 더 들어가 3 개가 되고, 잘라내기가 **끝에서**
잘라 획의 마지막 점을 가져갔다. 내부 예산 0 을 허용해 `[첫 점, 끝 점]` 이 그대로 남는다.

### 듀티 예산의 트리거도 함께 고쳤다

PR #60 의 듀티 예산은 `paintedDabs >= FX_OIL_DAB_CAP` 로 "비싼 재칠"을 **대리 판정**했다. 사다리가
그 대리 지표를 무효화한다 — 캡 베드가 이제 캡에 정확히 앉지 않고 그 아래 띠에 앉으므로, 예산이
하필 그것을 위해 쓰인 획에서 조용히 안 걸린다.

대신 **이미 재고 있는 실제 비용**을 읽는다. 모든 오일 재칠에서 소요를 기록하고 쿨다운을
`t · (DIVISOR − 1)` 로 둔다. 싼 재칠은 그만큼 작은 쿨다운을 낳아 사실상 유예가 없고, 비싼 재칠만
비례해서 배분된다. 대리 지표가 하나 사라졌다.

### 아직 남은 것

캐리어의 33 ms 중 대부분은 격자와 무관하게 **매 이동 전량을 도는 두 단계**다:

| 단계 | 이동당 | 왜 남았나 |
| --- | --- | --- |
| `planImpastoReliefOverlayLanes` | 13–18 ms | 정착 접두 인자를 받지 않는다 |
| `planBristleLanesFromRuns` | 5–12 ms | 20k 런 전량을 다시 밴딩한다 |

둘 다 **이제서야** 증분화가 가능해졌다 — 베드가 안정되기 전에는 재사용할 접두 자체가 없었다.
픽셀을 바꾸지 않는 순수 증분화라 별도로 다룬다.
