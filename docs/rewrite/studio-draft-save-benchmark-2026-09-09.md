# Studio 초안 저장 고도화 벤치마크 및 구현 기록

- 기준일: 2026-09-09
- 대상: `/studio` 컷툰 편집기
- 구현 브랜치: `feat/studio-draft-save-center-20260909`
- 목표: 저장 엔진을 다시 만드는 것이 아니라, 이미 존재하는 내구 자동복구·서버 revision·공동편집 충돌 방지 기능을 사용자가 정확히 이해하고 제어할 수 있게 한다.

## 1. 현재 시스템 진단

기존 Studio 저장 계층은 이미 다음 안전 장치를 갖고 있다.

1. 브라우저 내구 저장소(OPFS/SQLite) 기반 자동복구 체크포인트
2. 문서별 leader/follower 조정과 writer lease를 통한 다중 탭 덮어쓰기 방지
3. 서버 `baseRevision` 기반 낙관적 동시성 제어
4. 공동편집 CRDT 동기화·승인 장벽 이후 서버 저장
5. 서버 revision 비교·복원과 로컬 체크포인트 패널
6. 탭 종료 전 저장 가드와 비상 프로젝트 내보내기
7. 필수 작품 정보가 없을 때 정확한 저장 의도를 보류했다가 이어가는 `pendingSaveIntent`
8. 기존 원고 하이드레이션 완료 전 저장을 막는 런타임 상태

핵심 결함은 저장 기능의 부재가 아니라 **상태 의미가 여러 화면에 흩어져 있다는 점**이었다. 사용자는 아래 질문에 즉시 답하기 어려웠다.

- 지금 보이는 “저장됨”이 이 기기 복구 저장인지 서버 revision인지
- 오프라인 작업이 기기에 남았는지, 서버 전송까지 끝났는지
- 같은 문서를 연 다른 탭 중 어느 탭이 로컬 저장을 담당하는지
- 서버 저장 실패가 네트워크 문제인지 revision 충돌인지
- 원고를 아직 불러오는 중이거나 불러오기에 실패했는데 저장해도 되는지
- 제목 등 필수 정보 때문에 중단된 초안 저장을 어디서 이어가는지
- 실패 직후 어디에서 버전 기록을 열고, 어디에서 비상 백업을 받는지

따라서 이번 변경은 새 저장소나 별도 API를 만들지 않고, 기존 권위를 하나의 제품 표면에 투영한다.

## 2. 공식 제품 벤치마크

### Figma

공식 문서는 버전 기록에 자동 체크포인트를 누적하면서 현재 버전을 계속 갱신하고, 사용자가 중요한 버전에 이름·설명을 붙이고 이전 버전을 비파괴적으로 복원할 수 있다고 설명한다. 또한 오프라인 변경은 브라우저에 저장하고 재연결 시 동기화하며, 툴바 아이콘으로 연결 및 저장 시도 상태를 드러낸다.

- [View a file's version history](https://help.figma.com/hc/en-us/articles/360038006754-View-a-file-s-version-history)
- [What can I do offline in Figma?](https://help.figma.com/hc/en-us/articles/360040328553-What-can-I-do-offline-in-Figma)

적용 판단:

- 채택: 지속적인 compact 상태, 오프라인/동기화 구분, 버전 패널의 직접 진입, 덮어쓰지 않는 복원 원칙
- 기존 충족: 서버 revision 비교·복원, 로컬 변경 내구 저장
- 후속 후보: named milestone에 설명·관련 작업 링크 추가

### Adobe Photoshop Cloud Documents

Photoshop은 자동 저장된 클라우드 버전을 타임라인과 썸네일로 탐색하고, 버전 이름·설명·표시·검색·필터·이전 버전 되돌리기를 제공한다. 오프라인 사용 가능 여부도 온라인 전용 문서와 구분한다.

- [Manage cloud documents and version history](https://helpx.adobe.com/photoshop/using/manage-cloud-documents-photoshop.html)

적용 판단:

- 채택: 서버 revision 번호와 마지막 확인 시각을 상태 센터에서 명시
- 기존 충족: 이전 revision 비교·복원
- 후속 후보: revision 썸네일, 이름·설명, 검색·필터

### Clip Studio Paint

Clip Studio Paint는 강제 종료 복구 정보, 5~60분 정기 저장, 덮어쓰기 또는 복구 정보 저장, 홈 이동·카메라 기능·새 문서/열기/내보내기 전 위험 경계 저장을 분리해 제공한다.

- [Can you tell me about Auto Save?](https://support.clip-studio.com/en-us/faq/articles/20240009)

적용 판단:

- 채택: “기기 복구”와 “서버 초안”을 별도 카드로 노출하고 프로젝트 백업을 위험 시 강조
- 기존 충족: pagehide/종료 경계 플러시, 자동복구, 내보내기
- 후속 후보: 장시간 렌더·대형 가져오기 직전 사용자 명명 체크포인트

### Krita

Krita는 일반 백업, 번호가 붙는 incremental backup, 원본을 유지하며 새 번호로 저장하는 incremental version을 구분한다. 여러 개의 알려진 정상 상태를 유지하는 비용과 목적을 사용자에게 명확히 설명한다.

- [Autosaving and backup files](https://docs.krita.org/pt_BR/user_manual/autosave.html)

적용 판단:

- 채택: 실패 시 프로젝트 백업을 별도 안전 수단으로 명확히 제시
- 기존 충족: 서버 revision과 로컬 체크포인트가 서로 다른 복구 축으로 존재
- 후속 후보: 보관 정책·예상 저장 용량 표시

### Notion

Notion은 편집 중 일정 주기로 버전을 만들고 마지막 편집 후에도 버전을 추가하며, 버전별 변경 하이라이트와 전체 복원 또는 일부 콘텐츠 복사를 제공한다.

- [Delete & restore content / Version history](https://www.notion.com/help/duplicate-delete-and-restore-content)

적용 판단:

- 채택: 자동 저장 주기 설명과 버전 기록 접근성 강화
- 기존 충족: revision 비교 후 복원
- 후속 후보: 웹툰 문서 단위 diff 요약(페이지 추가/삭제, 요소 수, 텍스트 변경)

## 3. 구현한 제품 경험

### 3.1 상시 “초안 저장 센터”

편집기 우측에 현재 상태를 압축한 버튼을 상시 제공한다.

- `서버 rN 확인`: 서버에 복원 가능한 revision이 확인된 상태. 현재 메모리의 모든 변경까지 저장됐다고 단정하지 않는다.
- `원고 불러오는 중`: 기존 문서 하이드레이션이 끝나기 전 빈 상태 저장을 차단한 상태
- `원고 복구 확인`: 원고 하이드레이션 실패 후 기존 버전·체크포인트 복구가 필요한 상태
- `저장 정보 입력 필요`: 필수 작품 정보 때문에 정확한 초안 저장 의도가 보류된 상태
- `초안 저장 중`: 실제 기존 서버 저장 핸들러가 실행 중인 상태
- `공동 변경 동기화 중`: CRDT/협업 작업이 저장 좌표에 도달하기 전 상태
- `오프라인 · 기기 저장`: 서버와 분리된 로컬 보호 상태
- `연결 후 저장 예약`: 사용자가 오프라인에서 서버 저장을 요청한 상태
- `복구 저장 확인`: OPFS/저장소 실패가 감지된 상태
- `저장 충돌 확인`: stale revision을 다시 덮어쓰지 않고 비교·복원으로 보내는 상태
- `서버 저장 실패`: 일반 서버 저장 실패 후 안전한 재시도가 가능한 상태

상태 버튼은 `aria-live="polite"`, 명확한 접근명, Escape 닫기 및 트리거 포커스 복원을 제공한다.

### 3.2 저장 권위 2단 분리

상세 패널은 저장을 한 문장으로 뭉개지 않고 두 카드로 분리한다.

- **이 기기**: local leader/follower, 내구 저장 실패·제한, 문서 잠금 조정 방식
- **서버 초안**: online/offline, saving, queued, sync pending, revision, 마지막 저장 확인 시각

요약 영역에는 기기 체크포인트 수, 서버 revision, 서버 버전 수, 마지막 서버 확인 시각을 각각 표시한다.

서버 revision이 있어도 현재 오프라인이면 녹색 “클라우드 저장 완료”처럼 보이지 않는다. 반대로 서버 오류가 있더라도 기기 복구가 정상인지 별도로 확인할 수 있다. 또한 compact 상태는 실제 dirty-generation 영수증 없이 “모든 변경 저장 완료”를 선언하지 않고, 확인 가능한 서버 revision만 표시한다.

### 3.3 오프라인 저장 예약

오프라인에서 “지금 서버에 저장”을 누르면 즉시 실패시키지 않는다.

1. 현재 원고의 현재 탭에 단일 저장 의도를 기록한다.
2. UI를 `연결 후 저장 예약됨`으로 전환한다.
3. `online` 이벤트가 오면 기존 `handleSave("draft")`를 한 번 호출한다.
4. 저장 중, 공동 문서 잠금, 원고 하이드레이션 미완료, 초안 메타데이터 입력 대기 상태에서는 실행하지 않는다.
5. 다른 원고로 이동하면 저장 센터를 재마운트해 이전 원고의 예약·오류 상태를 폐기한다.

이 예약은 문서 콘텐츠를 새로운 브라우저 저장소에 복제하지 않는다. 탭 세션의 의도만 보관하며, 실제 내용의 내구성은 기존 OPFS/SQLite 자동복구가 담당한다.

### 3.4 저장 전 안전 게이트

#### 하이드레이션 게이트

기존 원고가 아직 완전히 로드되지 않았으면 수동 서버 저장과 프로젝트 백업을 비활성화한다. 하이드레이션이 실패하면 빈 문서를 새 revision으로 쓰지 않고 `버전·복구 열기`를 기본 행동으로 제공한다. 체크포인트 패널은 서버 문서가 없어도 로컬 복구 지점 생성·복원을 지원하므로 항상 접근할 수 있다.

#### 작품 정보 게이트

기존 저장 파이프라인이 `pendingSaveIntent === "draft"`를 만들면 저장 센터도 `저장 정보 입력 필요`를 표시한다. 기본 행동은 새 저장 호출을 만드는 것이 아니라 기존 `onContinuePendingSave`를 호출해 제목 등 필수 정보를 채운 뒤 **정확히 같은 초안 저장 의도**를 이어간다. 게시 의도는 초안 센터가 가로채지 않는다.

#### 충돌 게이트

revision 충돌 메시지를 일반 서버 실패와 구분한다. 일반 실패는 재시도를 제공하지만, 충돌은 `버전 비교·복원`을 기본 행동으로 바꾼다. 자동 force overwrite나 반복 blind retry는 하지 않는다.

### 3.5 실패 우선순위와 복구 동선

사용자에게 가장 위험한 상태가 먼저 보이도록 우선순위를 고정했다.

1. 원고 하이드레이션 실패
2. 기기 복구 저장 실패/저하
3. 원고 하이드레이션 진행
4. 공동 문서 잠금
5. 필수 작품 정보 입력 대기
6. 서버 저장 실패 또는 revision 충돌
7. 실제 저장 진행
8. 오프라인 재시도 예약
9. 오프라인
10. 공동 변경 동기화
11. 서버 revision 확인 완료
12. 기기 전용 보호/초기 준비

오류 화면에서는 별도 저장 구현 대신 기존 제품 권위로 이동한다.

- `지금 서버에 저장` / `서버 저장 다시 시도` → 기존 save pipeline
- `초안 저장 계속` → 기존 `pendingSaveIntent` continuation
- `버전 비교·복원` / `버전·복구 열기` → 기존 체크포인트 및 서버 revision 패널
- `프로젝트 백업` → 기존 프로젝트 내보내기

revision 충돌은 자동 force overwrite하지 않는다. 기존 비교·복원 흐름을 사용한다.

## 4. 아키텍처 불변식

이번 구현은 다음을 의도적으로 하지 않는다.

- 별도 `fetch` 또는 API 클라이언트 호출
- 새 IndexedDB/localStorage 저장소
- 문서 내용을 UI 상태나 진단 로그에 복제
- 기존 revision fencing 우회
- follower 탭의 로컬 저장 권위 탈취
- 하이드레이션 전 빈 문서 저장 또는 백업
- 충돌 시 자동 덮어쓰기
- 서버 스키마 또는 저장 포맷 변경

`StudioDraftSaveCenter`는 기존 핸들러와 신뢰성 스토어의 관찰자/오케스트레이터일 뿐이다. 이 경계는 정적 제품 테스트로 고정한다.

## 5. 테스트 매트릭스

| 시나리오 | 기대 결과 |
|---|---|
| 정상 온라인 + 서버 revision | `서버 rN 확인`, 기기/서버 상태 별도 표시 |
| 원고 하이드레이션 중 | 서버 저장·백업 비활성, 빈 문서 저장 호출 없음 |
| 원고 하이드레이션 실패 | `버전·복구 열기`, 서버 저장 호출 없음 |
| 초안 작품 정보 입력 대기 | 기존 continuation 정확히 1회 호출, 새 저장 호출 없음 |
| 오프라인 진입 | 서버 상태는 오프라인, 로컬 leader면 기기 보호 표시 |
| 오프라인에서 수동 저장 | 서버 호출 0회, 재연결 예약 표시 |
| 재연결 | 기존 저장 핸들러 정확히 1회 호출 |
| 원고 전환 | 이전 원고의 탭 세션 예약·오류 상태 폐기 |
| OPFS/저장소 실패 | 이전 정상 상태보다 높은 위험 상태와 백업 안내 |
| 서버 revision 충돌 | 비교·복원 패널 열기, 강제 덮어쓰기/재시도 없음 |
| 공동 문서 잠금 | 저장 버튼 비활성 및 권한/잠금 안내 |
| 버전 버튼 | 기존 체크포인트 패널 열기 |
| 백업 버튼 | 기존 프로젝트 내보내기 호출 |

## 6. 후속 고도화 제안

이번 MR은 기존 서버 계약을 변경하지 않고 즉시 제공 가능한 신뢰성·가시성 범위를 구현한다. 다음 단계는 서버 스키마 및 제품 정책 합의가 필요한 별도 작업으로 분리한다.

1. named revision: 제목, 설명, 마일스톤/이슈 연결
2. revision thumbnail과 페이지 단위 visual diff
3. 보관 정책 및 용량 예산 UI
4. 여러 기기의 미전송 변경 큐와 사용자 검토 병합
5. 대형 가져오기·일괄 변환·게시 직전 자동 체크포인트
6. 관리자용 저장 SLO: 성공률, p95 지연, 충돌률, 복구 성공률
