# 다중 획 시나리오 검증 — 2026-09-03

오너 지시: "시작점 끝점 교차 다른 브러시하고 혼합 선 등등 최대한 다양하게 테스트하면서 품질,
질감, 성능, 깜빡임, 드로잉 중과 완료선과의 괴리 모두 고도화", "큰 원을 그려서 장획 시 이슈 확인,
꺾임도 자연스러운지 확인".

장획 매트릭스(`verify-studio-brushes.mts`)는 브러시마다 **직선 한 획**만 긋는다. 이 회차에서
붙인 `verify-studio-brush-scenarios.mts` 는 그 한 획이 절대 밟지 못하는 제스처를 돌린다.

| 시나리오 | 무엇을 재는가 |
| --- | --- |
| `curve` | S 커브에서 라이브↔커밋 실루엣, 양 끝 캡 |
| `circle` | 360 표본 닫힌 원 — 이 매트릭스에서 가장 긴 연속 경로, 시작·끝이 만나는 이음매 |
| `corners` | 90°·예각·반사각 지그재그 — 꺾임이 라이브에선 둥글고 커밋에선 각지면 결함 |
| `cross` | 같은 브러시 두 획의 교차부 — 깜빡임·톤 이동 |
| `mixed-over/under` | 젖은 매체 위 마른 매체, 그 반대 |
| `endpoints` | 탭·짧은 플릭·중간 획의 pointer-down/up 캡 |
| `eraser-cross` | 획 위를 지우개로 교차 — 지워진 틈이 남는지 |

매 획마다 baseline / 라이브(중간) / 라이브(마지막 표본) / 손 뗀 직후 / 릴리스 후 8프레임 /
정착 프레임을 찍고, 제스처 동안 메인 스레드 롱태스크와 애니메이션 프레임 정체를 표집한다.
스크린샷 자체가 만드는 롱태스크는 캡처 구간과 겹치는지로 분리해 앱 몫만 보고한다.

**실행 환경이 결정적이다.** 기존 게이트는 헤드리스 셸(SwiftShader)에서 돈다. 거기서는 WebGPU
라이브 잉크 레인이 애초에 선택되지 않아, 아래 두 결함이 190 브러시 전수 게이트를 통과했다.
시나리오 검증기는 기본값이 `channel: chromium`(실제 GPU) 이다.

## 고친 것

- **반투명 직접잉크 브러시가 아무것도 그리지 않음**(마커 0px). GPU 레인이 준비 증명 없이는
  렌더할 수 없는 스타일인데도 레인을 선택해 두고, 결정이 not-ready 를 돌려주자 획 자체를
  거절했다("선택 거부 사유: opacity"). 레인에 들어가기 전에 스타일을 판정해 Canvas2D 로 간다.
- **지우개가 GPU 브라우저에서 아예 동작하지 않음**("선택 거부 사유: eraser"). 같은 원인이다 —
  이 레인의 준비는 항상 `transparent-overlay` 라 destination-out 이 아래 커밋 캔버스를 지울 수
  없고, 결정은 절대 ready 가 되지 않는다. 채우기·대칭도 같은 이유로 스타일 게이트에 넣었다.
- **직전 획의 2초 지연 커밋 창 안에 그은 두 번째 획이 거절됨**. 대기 큐를 붙들고 있던 것은
  영수증이 아니라 유휴 타이머였다. 새 획이 시작되면 그 커밋을 flushSync 로 끝내고 가드를 읽는다.
  실측: 해칭 간격 0.6초에서 100% 거절 → 0%.
- 두 거절 모두 배너를 띄우며 캔버스를 38px 밀어, 그리는 도중 화면이 튀었다.

## 원·꺾임 육안 확인 (반지름 150px, 360 표본)

pen · gpen · maru-pen · pencil · brush · watercolor · oil · airbrush · charcoal 전부 라이브
마지막 프레임과 정착 프레임이 일치했고, 이음매·꺾임 모두 판정 오류 0.

- 원의 이음매: pen 은 매끄럽게 닫히고, maru-pen 은 양 끝이 테이퍼로 가늘어져 머리카락만 한 틈이
  남는다 — 라이브와 커밋이 같은 모양이므로 세필 nib 의 정직한 거동이다.
- 꺾임: 지그재그의 90°·예각·반사각 모두 라이브에서 각지고 커밋에서도 각졌다. 둥글게 뭉개지거나
  스파이크가 튀는 브러시는 없었다.

## 완성된 획을 라이브 지연 기한으로 지운 결함

핀 영수증 워치독은 모든 요청에 300ms 를 준다. 포인터 프레임에는 맞는 예산이지만, **손을 뗀 뒤의
최종 영수증**에는 틀린 질문이다 — 그때는 아무것도 움직이지 않으므로 그 기한은 메인 스레드가 얼마나
바쁜지만 쟀고, 지연 커밋 렌더가 그 예산을 넘기는 순간 제품이 완성된 획을 지웠다("WebGPU 라이브 잉크
엔진을 더 이상 사용할 수 없어 현재 획을 취소했습니다"). 0.6초·3초 두 케이던스에서 모두 재현됐고
배너가 캔버스를 38px 밀었다. 요청 단위 예산을 허용해 손 뗀 뒤 3개 지점만 2초로 바꿨다.
검증: 20획 연속에서 배너 0회, 캔버스 이동 0px.

## 드로잉 중 깜빡임 — 하니스가 볼 수 없는 구조였다

위 "188 레인 깜빡임 0건"은 틀린 결론이었다. 검증기는 손 뗀 **뒤** 프레임만 시리즈로 찍고 그리는
중은 한 장만 찍었다. 스크린샷은 한 장당 렌더러를 ~100ms 막으므로 시리즈로 찍으면 정지 프레임의
나열이 될 뿐이라, CDP `Page.startScreencast` 로 컴포지터가 **실제로 표시한 모든 프레임**을 받게
고쳤다(`analyzeStudioBrushScenarioInStroke`). 판정 계약은 가장 단순한 것 하나다 — 제스처는 잉크를
더하기만 하므로, 손을 떼기 전에 화면의 잉크가 러닝맥스 대비 크게 줄었다가 다시 칠해지면 그것이
사용자가 본 깜빡임이다.

운영(`toonspectrum.vercel.app`)·로컬 빌드 동일 재현, 곡선 한 획:

| 브러시 | 깜빡임 | 비고 |
| --- | --- | --- |
| pen | **110회, 100%** (~220 프레임 중) | 이 문서의 주제 |
| web-blend-softener | 32회, 100% | 같은 GPU 레인 |
| ink-wash--sumi-core | 3회, 68% (초반) | 별개 원인 |
| watercolor | 1~2회 (초반) | GPU 캔버스 1x1, 엔진 미초기화 레인 — 미결 |
| gpen·pencil·marker·velvet-charcoal·dry-rake 등 | 0 | |

`dry-rake`·`velvet-charcoal` 의 첫 보고는 검출기 버그였다 — 스크린캐스트 메타 타임스탬프가 도착
순서와 시간 순서가 달라 최악 지점이 −103ms 로 잡혔다. 정렬 후 둘 다 깨끗하고 진짜 문제는
롱태스크(643ms)다. 바탕 없는 지우개의 `post-release-empty` 도 오진이었다.

**근본원인(A/B 115→0)**: 펜 획은 Konva 도 라이브 오버레이도 아닌 **WebGPU 컴포지터 캔버스**에
그려진다. 코디네이터가 모든 GPU 제출을 표면 파괴로 취급해 포인터 샘플마다 컴포지터 루트를
`visibility:hidden; opacity:0` 로 감추고, 정확한 영수증이 와야 다시 보였다. WebGPU 영수증은
`device.queue.onSubmittedWorkDone()` 뒤라 비동기 → 한 제스처에 118회, 중앙값 25ms 의 은닉.
Canvas2D 는 같은 태스크에서 동기로 영수증을 내서 안 깜빡인다. 픽셀은 살아 있었다 — 은닉 중
118/118 샘플에서 잉크가 읽혔다. 감춰졌을 뿐이다.

journal-append 는 retained 타일에 `loadOp:"load"` 로 쌓여 표면을 파괴하지 않는다. 그래서 제출에
`surfaceContinuity: "append" | "rewrite"`(기본 `rewrite`, fail-closed)를 도입해 append 만 표시를
잇는다. 첫 영수증 전 프레임은 여전히 노출되지 않는다 — `gpuOverlayVisible` 이 그 전엔 false
라 모델에서 저절로 나온다. 적대 검증이 구멍 하나를 잡았다: append 절이 세션을 현재 표면에 묶지
않아 **봉인된 이전 획**(pointer-up 이 overlay 플래그와 expected 요청을 일부러 남긴다)이 새 획의
재작성된 표면을 영수증 없이 열어줄 수 있었다. `expectedGpuRequest.requestId ===
currentSurfaceRequestId` 로 묶었다.

레이어 프로브도 눈이 멀어 있었다 — `.konvajs-content` 만 봐서 펜의 모든 픽셀이 있는 컴포지터를
안 봤고, "어느 레이어도 안 변함" 이라는 오독으로 조사가 헛돌았다. 이제 GPU 컴포지터와 그 루트의
computed visibility 를 프레임마다 기록한다: 픽셀 읽기만으로는 "숨겨졌을 뿐"을 절대 알 수 없다.

## 글로우 장획 O(n²) — 해결

| 측정 (반지름 150px, 359 이동, 캔버스 없이 계획+추적) | 이전 | 이후 |
| --- | --- | --- |
| glow 한 획 | 9.78s | **0.44s** |
| glow 최악 이동 | 121.9ms | **4.6ms** |
| neon 한 획 | 0.50s | 0.03s |

세 내부 함수가 append-from-index 변형이 되고, 배치 플래너는 그것을 index 0 에서 한 번 돌리는
래퍼가 됐다 — 한 코드 경로라 갈라질 수 없다. 폴리곤 방출을 구간-국소 순서로 바꿔 배열이
append-only 가 되었고, 픽셀은 불변이다(같은 winding 강제 + nonzero 단일 fill → 순서 무관).
폴리곤 34,512 / 정점 483,648 전후 동일. 추적은 (획, 패스) 별 `Path2D` 로 유지하고 프레임마다
복사해 **단일 fill** — 두 번 채우면 겹침이 a + a(1−a) 로 합성된다.

조인 생략은 되돌렸다. 48 셸이 각각 다른 조인 부분집합을 버려 셸이 포개지지 않았고, 헤일로가
방사형으로 너덜해진 이유가 그것이다. 성능 게이트는 재지도 않는 레인을 통과시키고 있었다 —
글로우 프로브가 압력 빌더에서 멈춰 한 이동의 1/48 만 재고 있었다. 이제 48 셸 전 체인을 돈다.

## 연필 겹칠 — 해결, 그리고 도달 불가 프리셋

연필은 alias 패스 하나를 `opacityScale` 1.0 으로 칠하므로 셀 알파가 곧 요소 불투명도다. 0.85
에서는 5회차부터 한 8비트 계단도 못 더한다. `defaultOpacity` 를 0.55 로 내렸다(6회차에 0.99).
alias 프로필의 `opacityScale` 이 아니라 이 값을 내린 이유: `defaultOpacity` 는 그릴 때 DrawEl 에
박히므로 **새 획**만 달라지고 저장된 문서는 한 픽셀도 안 바뀐다. `opacityScale` 은 소급이다.

**단, 2B·6B·소프트 연필·색연필은 격리 상태라 사용자가 고를 수 없다.** 2B 변경(0.88→0.72)은
도달 불가 프리셋 편집이었다. 해롭진 않지만 커밋 메시지가 암시한 "재질 등급 순서" 는 사용자에겐
보이지 않는다.

## 브러시 선택 불가 신고 — 재현 실패

`scripts/verify-studio-brush-selectable.mts` 신설. 운영 190개 노출 프리셋 전부: 검색→클릭 선택
OK, 12개 탭 끝까지 마운트(질감 61/61), 190개 전부 획 남김. 격리된 70개(젤펜·볼펜·아크릴·2B 등)
는 피커 검색·커맨드 팔레트 어디에도 새어나오지 않는다. 지우개 카드는 aria-label 이
`"<이름>, 38% 지움…"` 이라 `/선택$/` 매처에 안 걸려 두 번 오진했다 — 제품이 아니라 검증기였다.
어느 브러시였는지, 검색인지 탭 브라우즈인지 알면 좁힐 수 있다.
