# Ranking architecture

ToonSpectrum ranking has one active production responsibility: deterministic scoring over the reviewed
catalog snapshot. Runtime live-ranking fetchers and schedulers have been removed. Every ranking result is
computed from the same committed catalog used by search, detail, calendar, and recommendations.

## Runtime contract

- Static default: `apps/web/public/data/ranking/<axis>-<type>.json`, generated by `scripts/build-static-catalog.ts`
- Filtered static engine: `apps/web/src/shared/catalog/catalog-static.ts`
- API fallback route: `GET /api/ranking`
- Controller: `apps/api/src/modules/catalog/catalog.controller.ts`
- Service boundary: `apps/api/src/modules/catalog/catalog.service.ts`
- Formula source: `packages/core/src/ranking.ts`
- Cache policy: `Cache-Control: no-store, max-age=0`
- External ranking fetches at request time: none

The browser normally reads precomputed ranking files or computes filtered rankings from the static catalog.
The Nest fallback uses the same query normalization, filters, and formula. Client components render the
returned items and evidence; they do not create a second ranking order.

## 카탈로그 데이터 경계와 수동 갱신

운영 카탈로그는 `apps/api/data/catalog.json.gz`입니다. 빌드가 이 파일을 정적 샤드로 변환하고,
Nest API는 같은 파일을 부팅 시 한 번 메모리에 로드합니다. 파일이 없거나 파싱에 실패하면 가짜 seed로
대체하지 않고 빈 카탈로그로 시작합니다.

배포된 서비스에는 다음 기능이 없습니다.

- 카탈로그 크롤 실행 API와 관리자 실행 버튼
- API 내부 수집 스케줄러와 파일 변경 폴링
- GitHub Actions 기반 주기 수집
- `catalog_snapshot` 또는 `catalog_ingest_run` DB 의존성
- 요청 시점의 외부 플랫폼 랭킹·연재상태 수집

갱신은 로컬 운영자가 아래 명령을 명시적으로 실행한 경우에만 시작됩니다.

```bash
pnpm --silent catalog:crawl:manual > /tmp/toonspectrum-catalog.json
pnpm catalog:update:manual
```

`catalog:update:manual`의 순서는 다음과 같습니다.

1. `scripts/crawl.mjs`가 선택된 공개 소스를 수집해 임시 JSON을 만든다.
2. `scripts/merge-catalog.mjs`가 기존 스냅샷을 base로 새 값을 upsert하고, 이번 실행에서 빠진 기존
   작품을 유지한다.
3. `scripts/validate-catalog.mjs`가 최종 병합 결과의 형태·전체 건수·플랫폼별 회귀를 검사한다.
4. 검증 통과 시에만 `catalog.json.gz`를 교체하고 `pnpm catalog:gen`으로 정적 파일을 다시 만든다.
5. 운영자가 건수·샘플·diff를 검토하고 커밋·재배포한다.

실행 중인 서버는 파일을 다시 읽지 않습니다. 새 데이터는 검토된 커밋이 배포되고 API 프로세스가
새로 시작될 때 반영됩니다.

### 수동 수집 설정

아래 값은 로컬 크롤러만 읽습니다. 배포 API의 환경 스키마에는 ingest 모드·주기·트리거 토큰이 없습니다.

- `WEBDEX_SOURCE_IDS`
- `WEBDEX_CRAWL_DELAY_MS`
- `WEBDEX_WEBTOON_CAP`
- `WEBDEX_WEBTOON_DETAIL_CAP`
- `WEBDEX_SERIES_BONUS_CAP`
- `WEBDEX_KAKAO_WEBTOON_CAP`
- `WEBDEX_LEZHIN_CAP`
- `WEBDEX_WEBTOON_FINISHED_PAGES`
- `WEBDEX_SERIES_PAGES_PER_GENRE`
- `WEBDEX_CRAWL_BUDGET_MS`

`WEBDEX_SOURCE_IDS`를 지정하지 않으면 `scripts/crawl.mjs`의 명시적 기본 목록을 사용합니다. `all`도
로컬 수동 실행에서만 의미가 있습니다.

### 수집 소스 확장 절차

현재 어댑터는 `scripts/crawlers/*.mjs`와 `scripts/crawl.mjs`에 연결됩니다. 새 플랫폼은 다음 순서로
추가합니다.

1. robots.txt, 이용약관, 공개 API·제휴 피드, 호출량 제한을 검토한다.
2. 로그인·성인인증·결제·CAPTCHA·비공개 앱 API 우회가 필요하지 않은지 확인한다.
3. 검색과 라우팅에 필요한 최소 메타데이터만 저장하도록 어댑터를 구현한다.
4. 로컬에서 소스 단독 실행과 전체 수동 실행을 반복하고, 플랫폼별 건수와 샘플 필드를 검토한다.
5. 검토가 끝난 소스만 `scripts/crawl.mjs`의 기본 목록에 추가한다.

429·403·지역 차단이 반복되면 해당 source id를 다음 수동 실행의 `WEBDEX_SOURCE_IDS`에서 제외합니다.
배포 서버나 별도 스케줄러가 대신 재시도하지 않습니다.

## 법적 리스크 완화 원칙

이 문서는 법률 자문이 아닙니다. 운영 전에는 플랫폼별 약관, robots 정책, 데이터베이스 제작자 권리,
저작권과 제휴 가능성을 별도로 검토해야 합니다.

1. **공식/허용 소스 우선**: 공식 API, 공개 데이터, 제휴 피드를 우선하고 금지된 경로는 사용하지 않는다.
2. **저장 범위 최소화**: 작품 메타데이터·공개 수치·원문 링크·출처 정보만 저장하며 본문, 회차 이미지,
   댓글 원문, 개인정보는 수집하지 않는다.
3. **호출량 통제**: 로컬 수동 실행에도 지연·cap·timeout을 적용하고 차단 징후가 있으면 즉시 중단한다.
4. **사람 검토**: 검증 스크립트 통과만으로 배포하지 않고 결과와 diff를 사람이 확인한다.
5. **출처와 추정값 공개**: 실수집 값과 추정 지표를 구분하고 스냅샷 버전과 산식 근거를 보존한다.

## 외부 실시간 랭킹 호출 없음

과거의 외부 live-ranking 어댑터와 갱신 스케줄러는 제거되었습니다. `refresh=true` 쿼리는 기존 URL
호환을 위해 파싱되지만 외부 네트워크 호출이나 카탈로그 갱신을 일으키지 않습니다. 랭킹은 항상 현재
프로세스가 부팅 시 읽은 스냅샷에 대한 산식 결과입니다.

## Ranking flow

1. Normalize query parameters.
2. Filter the in-memory snapshot by type, genre, platform, status, pricing, and minimum rating.
3. Run the deterministic formula with `rankBy`.
4. Attach formula evidence and reliability metadata based on estimated-stat share.
5. Return ranked items and insights without contacting an external ranking source.

The same snapshot and formula produce the same order for the same query. `refresh=true` does not bypass this
contract.

## 투명 산식 v2 — 기간 블렌딩 · 신선도 · 유도 사전값

`lib/ranking.ts`의 산식은 완전히 결정적입니다. `Math.random`은 물론 과거의 `seededRandom` 기간 변주(wobble)도 사용하지 않습니다 — 같은 카탈로그·같은 쿼리는 언제나 같은 순서와 같은 점수를 돌려줍니다. 기간 간 순위 차이는 전부 실제 신호의 가중 차이로 설명됩니다.

### 제거한 가짜 신호

- `periodFactor`: `seededRandom(id:axis:period)` 기반 곱셈 wobble(일간 ±25% 등) → **기간별 신호 블렌딩으로 대체**.
- 표시용 가짜 delta: 비모멘텀 축의 `seededRandom(...)` 순위 변동 → **실데이터 rankDelta 또는 결정적 추정으로 대체**.

### 기간별 신호 블렌딩 (`PERIOD_BLEND`)

```
최종점수 = 축점수 × (1 + momentum가중 × 모멘텀정규화 + cumulative가중 × 누적정규화) + ε(id)
```

| period  | momentum 가중 | cumulative 가중 | 의도 |
| ------- | ------------ | -------------- | ---- |
| daily   | 0.45         | 0.05           | 단기 모멘텀(실 순위변동·트렌드) 비중↑ |
| weekly  | 0.18         | 0.12           | 균형(기본) — delta 추정의 기준 기간 |
| monthly | 0.06         | 0.30           | 누적 신호(조회·관심·베이즈평점) 비중↑ |
| all     | 0            | 0.35           | 모멘텀 제외, 누적+평점 위주 |

- 모멘텀정규화 ≈ −0.64~1.06: `(clamp(rankDelta, ±15)/15 × 0.6 + clamp(trendingScore, 0~100)/100 × 0.4) × 신뢰계수`. 신뢰계수를 곱해 합성(추정) 모멘텀이 실데이터만큼 힘을 갖지 못합니다. 음수(하락)도 그대로 반영합니다.
- 누적정규화 0~1: `log10(조회)/9 × 0.45 + log10(관심)/7 × 0.3 + 베이즈정규화 × 0.25`. `hidden` 축만 예외로 조회·관심 대신 평점·평가수를 사용합니다(낮은 조회 역가중 철학과 모순 방지).
- ε(id): id의 FNV-1a 해시 기반 극소 타이브레이크(< 1e-6). 점수가 완전히 같은 작품의 순서를 결정적으로 고정할 뿐, 1e-6을 넘는 점수 차이에는 어떤 영향도 없습니다.

### 연재 신선도 (popular / trending 한정)

연재 활동 메타데이터(`status`, `updateDays`)로 휴재·완결작이 과거 누적 신호만으로 실시간 상위를 점유하지 못하게 합니다.

| 상태 | popular | trending |
| ---- | ------- | -------- |
| 연재중 + 연재요일 보유 | ×1.05 | ×1.05 |
| 연재중(요일 미상) | ×1.00 | ×1.00 |
| 휴재 | ×0.93 | ×0.85 |
| 완결 | ×0.95 | ×0.80 (제외 대신 감쇠) |

### 베이즈 사전값(C·m) 카탈로그 유도

하드코딩(C=4.0, m=800) 대신 `rankBy` 호출 시 카탈로그 분포에서 1회 유도하고 WeakMap으로 캐시합니다.

```
C = Σ(가중 × min(5, 평균평점)) / Σ(가중)   # 가중 = 실수집 표본 ratingCount, 추정 표본은 ratingCount × 0.25
m = 평가 보유작 ratingCount 중앙값
클램프: C ∈ [3.2, 4.6], m ∈ [50, 5000]
폴백: 평가 보유작 8편 미만이면 기본값(C=4.0, m=800)
```

`explainScore`는 공개 시그니처(`(title, axis)`) 유지를 위해 마지막 `rankBy`가 유도한 사전값을 표시에 사용합니다(랭킹 행은 항상 rankBy 결과에서 펼쳐지므로 일치). rankBy 호출 전이라면 기본값으로 표시됩니다.

### 크로스플랫폼 융합

- 도달 가중(reach)은 **최댓값 플랫폼 기준 유지** — 군소 플랫폼 여러 곳을 합산해도 메이저 1곳을 넘지 못합니다.
- 멀티플랫폼 유통작(서로 다른 플랫폼 2곳 이상)은 '검증된 IP' 보너스로 추가 플랫폼당 +2%, 최대 +6%를 받습니다(popular의 인기 성분과 trending의 백분위 성분에 곱셈).
- 인기 백분위 지수감쇠(`exp((pct−100)/2.5)`)와 신뢰계수(실데이터 1.00~1.06 / 추정 0.78~0.80) 메커니즘은 그대로입니다.

### 순위 변동(delta) 정직화

- `popular`/`trending`: 실데이터 `stats.rankDelta`를 그대로 노출합니다(없으면 0).
- 그 외 축: 주간(기준 블렌드) 순위 대비 현재 기간 순위의 차이를 ±5로 클램프한 **결정적 추정**만 노출하고 `deltaEstimated: true`로 표식합니다. weekly는 기준 기간 그 자체이므로 0입니다.
- `insights.rising`은 양의 delta가 실제로 있을 때만 채워집니다(0을 상승으로 과장하지 않음).

테스트는 `lib/__tests__/ranking.test.ts`(결정성·기간 신호 차이·seededRandom 미사용 소스 검증·신선도·C/m 유도·delta 정직화)와 `lib/__tests__/cross-platform-popularity.test.ts`(멀티플랫폼 보너스·도달 최댓값 원칙)가 보호합니다.

## Reliability model

Every response includes `meta.reliability`.

- `confidence`: interpretation score from 0 to 100
- `level`: `high`, `medium`, or `low`
- `fallbackReason`: explains that the active path is snapshot/formula based
- `estimatedCount` / `estimatedShare`: how much of the ranked set relies on estimated core stats
- `basis`: concise evidence used to interpret the score

Confidence is disclosure metadata, not another ranking factor.

## UI rules

- Describe the result as snapshot/formula based; do not label it live data.
- Show confidence and evidence near ranking controls.
- Mark estimated statistics clearly.
- Do not show `LIVE #n` badges or live-source success states.
- Keep ranking usable even when the dynamic API is unavailable by falling back to generated static files.

## 스냅샷 모드 교차 검증 체크리스트

- 같은 스냅샷과 같은 쿼리가 반복 실행에서 동일한 순서와 점수를 반환한다.
- `refresh=true`가 외부 네트워크 요청이나 결과 순서 변경을 만들지 않는다.
- `meta.reliability.fallbackReason`이 스냅샷 산식 경계를 설명한다.
- UI가 실시간 데이터로 오인할 수 있는 문구·배지·상태를 표시하지 않는다.

## Data boundaries

- `apps/api/data/catalog.json.gz`: reviewed catalog source bundled with deployments
- `apps/web/public/data/*.json`: generated CDN catalog and ranking surfaces
- `apps/web/src/shared/catalog/catalog-static.ts`: browser-side static query boundary
- `packages/core/src/catalog/catalog-store.ts`: in-memory snapshot used by server read models
- `apps/api/src/server/catalog-file.ts`: read-only bundled-file parser
- `apps/api/src/server/catalog-loader.ts`: one-time API startup loader
- `apps/api/src/modules/catalog/*`: external API boundary
- PostgreSQL: dynamic product data only; no catalog snapshot or ingest-run storage

## Runtime configuration

There are no runtime catalog-ingest or live-ranking environment variables. `WEBDEX_*` crawl controls are for
local manual commands only. The API may use `WEBDEX_CATALOG_FILE` or the legacy path alias
`WEBDEX_CATALOG_GZ` to select a read-only bundled file, but it never writes or polls that file.
