### 생성 아트와 출처

첫 생성 묶음으로 내장 `image_gen` 도구의 PNG 6개를 실제 화면에 연결했다. 이후 추가한 테마 캐릭터와 NPC는 아래에 구분한다. [아트 원장](../../apps/web/public/assets/virtual-studio/experience-v8/art-manifest.json)에 프롬프트, 파일명, 바이트 수, SHA-256과 생성 출처를 남겼다.

| --- | --- | --- |
| 공중섬·숲·해안·야경 원경 | `sky.png`, `forest.png`, `coast.png`, `city.png`; 각 1536×1024 | 네 가지 배경 환경 |
| 초기 가구 16종 | `furniture.png`; 1254×1254, 투명 4×4 atlas | 기존 장식과 드로잉 데스크·책장·원고 리뷰 보드·소파의 초기 연결. 이후 스타일별 원본 자산을 추가했다. |

생성 도구가 모델 버전을 노출하지 않아 **ImageGen 2.5 사용 여부를 확인하거나 인증할 수 없다**. 원장의 `modelVersion`은 `null`로 유지한다. 배경·환경과 장소 선택 화면에 노출되던 모델 기술명은 각각 나만의 공간 연출, 다양한 작업 공간으로 바꿔 특정 버전을 보증하는 UI 표현을 제거했다. 요청 해상도와 실제 출력 크기를 구분하고 가구 프레임은 실제 1254px 크기를 기준으로 분할한다. 지형은 313.5px 셀을 표시용으로 사용한다.

원장에 보존한 외부 이미지 생성 프롬프트는 재현 근거이므로 영어 원문을 유지하는 언어 정책 예외다. 사용자 UI와 이 문서의 설명은 한글을 기본으로 한다. 생성 여부와 파일 무결성 확인은 모든 타일 경계가 시각적으로 완전하게 이어진다는 증명과 다르다.

후속으로 웹툰·파스텔·레트로·먹선·네온마다 하늘·숲·해안·야경 원경 4개를 별도 생성해 PNG 20개를 추가했다. 기존 공중섬 원경 4개와 합쳐 **6개 스타일 × 4개 배경의 24개 독립 원본**이며 모두 실제 1536×1024다. 환경 선택 URL은 현재 스타일의 원본을 가리킨다. 가구·랜드마크·바닥과 함께 원경도 스타일별 작화를 사용한다.

현재 일반 아트 원장에는 PNG 50개, 별도 NPC 원장에는 4개가 등록되어 있다. [전체 자산 무결성 테스트](../../apps/web/src/domains/creator/virtual-space/studio-virtual-space-experience-integrity.test.ts)는 디렉터리의 PNG 54개와 두 원장의 목록이 일치하는지, 모든 파일의 SHA-256·바이트 수·PNG 형식·치수가 일치하는지 확인한다. 원경 URL 도우미를 직접 사용해 24개 URL의 실제 파일과 원장 연결, 서로 다른 원본 해시도 검사했다. 이번 게이트는 PNG를 압축하거나 편집하지 않았다.

### 테마 캐릭터와 전용 NPC

- 공중섬·웹툰·파스텔·레트로·먹선·네온에 서로 다른 원본 플레이어 PNG 6개를 등록했다. 다섯 원본은 1536×1024, 네온은 1774×887이다. 각 원본은 아래·오른쪽·왼쪽·위의 네 방향과 걷기 4장, 대화, 인사, 앉기, 작화·검수 동작을 담은 32개 프레임을 제공한다.
- 테마 대표 캐릭터는 명시적으로 선택해야 적용된다. 테마 전환으로 기존 사용자의 캐릭터 정체성을 자동 교체하지 않으며 전용 원본을 다른 테마 색으로 다시 칠하지 않는다.
- 실제 생성 위치가 균등 격자와 일치하지 않는 원본은 알파 영역을 읽어 측정한 정수 사각형으로 표시한다. PNG를 재가공하지 않고 프레임별 폭·높이, 발 기준, 머리 상부 중심을 메타데이터로 기록한다. 팔 동작이 넓어져도 전체 외곽 너비가 캐릭터 가로 기준을 끌고 가지 않도록 했다.
- 안내 로봇·검수 코디네이터·자료 사서·카페 직원에 전용 NPC 원본 4개를 연결했다. 각각 1774×887의 32프레임이며 합계 6,989,292바이트다. 기존 8개 NPC의 식별자와 업무 목적·동선을 보존하고, 신규 네 캐릭터는 플레이어 선택 목록에 노출하지 않는다. 한 NPC의 걷기와 업무 동작은 동일 텍스처 하나를 공유한다.
- 플레이어 6개 원본은 SHA-256·크기·RGBA, 32개 정수 프레임의 비중첩, `alpha > 100`인 원본 픽셀 누락 0, 네 방향 걷기 프레임의 상이성, 발 기준과 머리 중심을 자동 검사했다. NPC도 원본 해시·크기와 32개 영역·동작 연결을 검사하고 알파 분석에서 누락 0을 확인했다. 이는 모든 행동의 예술적 완성도나 실기기 성능 검증을 대신하지 않는다.

### 서버 상태 표시와 재연결

2026-09-27 19:05~19:06 KST에 운영 상태를 인증 정보 없이 읽기 전용으로 확인했다. `/api/health/live`와 실시간 coordinator의 `/health`, `/api/auth/session`, `/api/health/capabilities`는 모두 HTTP 200을 반환했다. capabilities 응답의 프로젝트 읽기·클라우드 저장·실시간 협업은 `available`이었다. Edge liveness는 Core API·DB 성공을 뜻하지 않으며, 이 응답들은 인증된 참여·다중 사용자 동기화·저장 내구성 검증이 아니다. 사용자 내용·쿠키를 기록하거나 운영 데이터를 변경하지 않았다.

클라이언트 테스트에서는 다음 오류를 재현하고 수정했다.

- capabilities 본문이 비어 있거나 잘못된 형태인데도 사용 가능으로 받아들이던 판단을 수정했다. 프로젝트 읽기와 클라우드 저장이 각각 `available` 또는 `degraded`인지 확인한다.
- 이전 상태 점검의 JSON 처리가 늦게 끝나면 새로운 상태나 실제 API 성공·실패를 덮어쓸 수 있었다. JSON 처리 후에도 현재 요청인지 확인하고, 실제 API 결과가 들어오면 대기 중인 상태 점검을 취소한다. 중단·시간 초과 이후의 늦은 응답도 상태를 되돌리지 못한다.
- 연결 후 네트워크가 끊어진 상황에서 재접속이 권한 거부 또는 복구 불가능한 이력 상태로 끝나도 재시도 타이머가 이어질 수 있었다. 종료 상태인 `revoked`에서는 예약과 실행을 모두 차단한다. 일시적 오류의 기존 재연결 동작은 유지한다.

회귀 테스트로 느린 본문 응답과 실제 요청 결과의 순서 역전, 중단·시간 초과, 재연결 뒤 권한 거부·이력 복구 불가 상태를 검증했다. 핵심 소스는 [연결 상태 판단](../../apps/web/src/domains/creator/offline/studio-connectivity.ts), [순서 역전 회귀](../../apps/web/src/domains/creator/offline/studio-connectivity.runtime.test.ts), [실시간 재연결](../../apps/web/src/domains/creator/studio-realtime-provider-runtime.ts)이다. 이 변경은 클라이언트 오류 수정이며 운영 서버 설정·환경변수·DB·배포를 변경하지 않았다.

## 업무 시작과 움직임 후속 개선 — 2026-09-27

사용자가 배포 화면에서 목적과 행동을 이해하기 어렵고 움직임이 어색하다고 지적한 뒤, 첫 진입을 웹툰 작업 시작 안내로 바꿨다. 실제 현재 작품의 작업·마감을 표시하고 작업함, 동료 찾기, 작업 자리로 연결한다. 개인 로컬 작업실은 실제 작품 목록과 새 작품 링크를 제공하며 접속 동료나 프로젝트 업무를 만들어 표시하지 않는다. 모바일 하단에도 작업 시작·동료 또는 내 캐릭터·작업 자리·추가 메뉴 네 동작을 남긴다.

같은 장소의 업무 버튼이 아무 이동도 하지 않던 문제를 고쳤다. 현재 방의 실제 목적지까지 걷고, 다른 장소로 이동한 뒤에는 새 가구 충돌 정보로 경로를 다시 확인한다. 예전 큰 월드의 팀 자리 좌표를 작은 내장 장소에 잘못 전달하지 않는다. 선호 자리는 사용자·작품·월드·편집 모드별로 기억하지만, 실제 점유는 도착 후 기존 서버 lease로 확인한다.

동료에게 다가가기는 실제 위치·거리·벽·가구 통과 가능성을 확인한다. 도착하면 대화 패널을 열며 초대와 미디어 시작은 사용자의 다음 명시 동작으로 남긴다. 집중·자리비움·차단·연결 상실·다른 작업 선택 시 접근을 취소하고 지연된 위치 보고가 이동을 다시 시작하지 못하게 한다.

Phaser의 `setDeadzone`은 추적 위치도 초기화하므로 같은 모드에서 매 프레임 재호출하지 않도록 수정했다. 내장 장소의 플레이어 걷기는 160 world units/s, 한 보행 주기는 108 world units로 조정했고 네 걷기 자세를 실제 이동 거리로 진행한다. 그림자도 같은 거리의 양발 접지 주기에 맞추며 멈춤·모션 감소 설정에서는 고정한다. 기존 사용자 월드와 NPC의 속도·원본 보폭은 유지한다.

후속 검증 근거는 기존 1,309개 실행과 합산하지 않는다.

## 원본 atlas 품질 게이트와 보행 연출 — current, 2026-09-28

이 절은 2026-09-28 `codex/virtual-studio-experience-20260928` 작업에서 앞 절의 `target` 중
기계로 확정할 수 있는 두 항목을 닫은 기록이다.

### 원본 atlas 배율·기준점 고정

앞 절의 검수는 12장 PNG의 알파 본문 범위를 측정한 정수 사각형을 남겼지만, 그 결과가 **모든 장소와
스타일에서 같은 배율과 기준점을 보존한다는 기계적 확인이 없었다.** 기준점이 틀어지면 가구의 배치
좌표·회전·물리 충돌체가 조용히 이동하고 어떤 테스트도 실패하지 않는다.

[atlas 품질 게이트](../../apps/web/src/domains/creator/virtual-space/studio-virtual-space-experience-atlas-quality.test.ts)는
192프레임 전부에 대해 다음을 고정한다.

- 6개 스타일 × 가구·랜드마크가 1254×1254 `explicit-frames` 16프레임을 제공하고, 공통 helper가 16개를 그대로 돌려준다.
- 프레임이 정수·비퇴화·원본 안이며 위치가 중복되지 않는다.
- 원본 자체의 겹침 예외 4건(잉크 가구 0·4, 웹툰 랜드마크 0·4) 외에 새 겹침이 생기면 실패한다.
- 기존 4×4 격자의 배율과 기준점을 보존하고, 축척 범위와 가로·세로 비율, 결정론을 확인한다.
- 범위를 벗어난 프레임 번호가 `NaN` 대신 전달된 크기를 돌려준다.
- 6개 스타일 × 랜드마크·가구·지형 자산 URL이 실제 1254×1254 원본을 가리킨다.

**측정한 프레임은 셀보다 조여서 192프레임 중 148개의 기준점이 `[0, 1]` 밖에 있다.** 이는
잘못된 값이 아니라 앞 절이 정한 계약의 결과다. 잘라 등록해도 배치가 움직이지 않으려면 원래
균등 셀의 고정점을 그대로 옮겨야 하고, 조인 프레임에는 원래 셀에 있던 투명 여백이 없기 때문이다.
이 값을 `[0, 1]`로 잘라내면 모든 가구의 충돌체가 이동하므로 고치지 않는다.

게이트가 실제로 실패하는지 프레임 축척 축소, 새 겹침, 프레임 인덱스 순서 뒤집음으로 확인했다.

### 보행 위상과 몸의 동동

배포 화면에서 "움직임이 어색하다"는 지적을 따라 Phaser 렌더러를 확인한 결과, 몸의 상하 진동이
**걷기 클립이 없을 때만** 동작하고 있었다. 반면 그림자의 맥동은 `gaitDistancePerCycle`이 있으면
항상 동작했다. 즉 걷기 클립이 있는 내장 장소에서 그림자만 맥동하고 캐릭터는 완전히 고정되어
서로 어긋난연출 그대로 렌더링되고 있었다.

`studioGaitBodyOffset`는 그림자와 **같은 이동 거리·같은 위상**에서 몸의 상하·좌우 진동을 만든다.
접지 순간 그림자가 가장 작아지므로 그때 몸도 가장 낮아진다. `offsetY`가 `(cos - 1)`에서 나오므로
몸이 내려가는 높이는 그림자가 줄어든 높이의 고정 배(87.5)로 비례한다. 정지·벽·모션 감소·입력
오류에서는 0이고, 보폭이 없는 기존 사용자 월드와 NPC는 원본 속도와 흔들림을 그대로 유지한다.

꾸미기 패널과 환경 패널에 이 차이와 브라우저 한정 저장을 함께 밝히고, 안내 문구가 실제로

## 정본 필터 첫 획 미저장 — current, 2026-09-29

앞 절이 "정본 필터 브라우저의 첫 획이 저장되지 않아 전체 검증이 실패했다"고 남긴 항목의
원인을 코드에서 확정하고 고쳤다.

원인은 획 추가 경로가 아니었다. `appendStrokeSamples`에는 첫 획 특수 분기가 없고
begin → append → finalize 흐름도 정상이었다. 문제는 **커밋 모드 판정**이었다.

- 짧은 획과 탭은 지연 배치 파이프라인을 건너뛰고 pointerup 태스크에서 즉시 커밋되어
  undo·자동저장의 권위가 된다(`studio-draw-pointer-release-plan.ts`). 긴 획만 지연 배치를 쓴다.
- 그 판정인 `isStudioImmediateFreehandCommit`는 `travel * viewScale <= 24`로 즉시 커밋 여부를
  정하고 `viewScale`은 `peekStudioStageCssScale()`를 쓴다.
- `peekStudioStageCssScale`은 스테이지가 있으면 `clientWidth / width`를 **검증 없이 그대로
  반환**했다. 같은 함수의 나머지 분기는 모두 유한성·양수·최솟값을 검사한다.
- 첫 레이아웃 전에는 `stage.width()`가 컨테이너보다 작다. 그래서 비율이 크게 부풀어
  `travel`이 아무리 짧아도 24px를 넘기고 **첫 획만** 지연 배치로 넘어가 저장되지 않았다.
  이후 획은 스테이지가 맞춰져 비율이 1에 가까워지므로 정상 커밋된다. 첫 획만 잃는 증상이
  이 불균형과 정확히 일치한다.

스테이지가 100, 컨테이너가 1600인 단계에서 `peekStudioStageCssScale()`가 `16`을 반환하고,
그 상태에서 `[0, 0, 2, 3]` 같은 짧은 획이 즉시 커밋으로 남지 않는 것을 테스트로 먼저
재현했다. 이제 비율이 뷰 줌 범위(`STUDIO_VIEW_ZOOM_MIN` 0.2 ~ `STUDIO_VIEW_ZOOM_MAX` 5)를
벗어나면 스테이지의 실제 변환으로 되돌린다. 정상 비율과 실제 줌, 긴 획의 지연 배기는 유지된다.

브러시 도메인 320파일 3800테스트와 `StudioDrawNode` 84테스트가 통과했고, 게이트는 테스트를
되돌리면 다시 실패한다. 앞 절이 남긴 서버 정본 ACK 검증은 여전히 별도 과제다.

## 테마 전환이 올바른 이유를 고정 — current, 2026-09-29

앞 절의 테마 변경 초기화 항목은 코드 수정이 남아 있지 않음을 확인했다. 원인이 될 가설을 세우고
소스로 검증한 결과 가설이 틀렸고, 그 판단을 그대로 남긴다.

가설은 "테마가 바뀌면 이미 등록된 프레임이 남아 새 테마가 그려지지 않는다"였다. 실제로
`registerStudioSceneAtlas`는 `texture.has(String(frame.index))`로 이미 등록된 프레임을 건너뛰고,
가구·랜드마크 원본은 테마마다 사각형이 다르다. 하지만 **가구·랜드마크 텍스처 키가 모두
`${artStyle}`을 포함**해 있어(`studio-experience-v8-furniture-${artStyle}`,
`studio-experience-v8-landmarks-${artStyle}`) 테마 전환마다 새 텍스처가 만들어진다. 따라서 키를
공유하는 상황이 아니었고 이 가설은 성립하지 않는다. 게이지를 통과시키려고 이 동작을 고치지 않았다.

대신 실제로 성립하는 계약을 고정했다. 이 렌더러의 테마 전환 정합성은 **텍스처 키가 테마를
포함한다는 사실 하나에 달려 있으며**, 깨지면 예전 테마의 사각형이 남은 채 조용히 잘못 그려진다.
다음 네 가지를 확인한다.

- 가구·랜드마크 텍스처 키가 테마를 포함한다.
- 가구는 테마마다 사각형이 실제로 다르다(모두 같다면 키를 나눌 이유가 사라진다).
- 같은 텍스처에 다른 테마를 등록하면 이전 프레임이 남아도 성공으로 끝난다. 즉 이 테스트가
  막는 회귀를 그대로 고정한다.
- 고양이·표정처럼 공유하는 균등 격자 원본은 테마와 무관하므로 나누지 않는다.

가구 키와 랜드마크 키에서 `${artStyle}`을 제거하는 변이로 게이트가 실제로 실패하는 것을 확인했다.

앞 절이 남긴 "정확한 PR HEAD의 필수 CI 확인"은 코드 작업이 아니라 CI 확인 과제다. 개발 탭에서만
보인 HMR·응답 지연은 정적 빌드 여섯 테마 전환이 모두 ready로 끝난 것으로 확인되어 제품 결함으로
다루지 않았다.
