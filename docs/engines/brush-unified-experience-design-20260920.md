# 브러시 통합 경험·품질·다양성 고도화 설계

상태: **현재 코드 감사 + 제안 설계**. 표시 문구 외의 통합 런타임과 새 브러시 후보는 구현 완료가 아니다.
검토 기준: main `7e7f99325852f052ab3470cdc71adb9f42d5ce4f`, 2026-09-20.

## 1. 제품 원칙

브러시 제작기는 별도 렌더링 데모가 아니라 실제 원고 런타임을 작은 테스트 문서에서 실행하는 편집기다. 사용자에게는 선·재료·반응을 보여주고 엔진 세대 표시는 제거한다. 내부 스키마, 공급자 구현 식별자, 자산 해시와 시드는 과거 획 재현을 위해 유지한다. 사용자 브러시 이름의 숫자를 임의로 지우지 않는다.

이는 모든 브러시에 하나의 라이브러리를 강제한다는 뜻이 아니다. 서로 다른 브러시는 전문 엔진을 사용할 수 있지만, 동일한 브러시는 제작·미리보기·그리기·정착·저장·재생·내보내기에서 같은 의미를 유지한다.

## 3. 일관성 계약

동일한 입력, 브러시 내용, 최종 적용값, 종이·바탕·도막 상태, 시간, 시드와 출력 프로필은 동일한 계산을 만든다. 서로 다른 바탕이나 건조 시각의 결과 차이를 엔진 불일치와 혼동하지 않는다. 같은 환경의 결정적 출력은 정확한 일치를 검사하고, 다른 GPU·브라우저는 색·알파·경계·시간 오차를 따로 검사한다.
제작↔원고는 자산 내용 해시를 공유한다. 라이브↔정착은 accepted 입력과 재료 상태를 인계한다. Undo는 픽셀뿐 아니라 안료·수분·두께를 복원한다. 내보내기는 재료 효과를 단색 벡터로 몰래 바꾸지 않는다. 지원 불가 기기는 원본 열람과 명시적 변환을 제공하되 조용히 다른 엔진으로 그리지 않는다.

## 4. 제안 아키텍처

`BrushAsset → 공통 지원 판정·검증·컴파일 → BrushSession → 제작 테스트 문서/원고/썸네일 → 단일 commit·Undo·저장·출력`.
새 패키지를 일괄 신설하지 않고 기존 Studio 경계를 재사용한다. 한 획의 표면 쓰기는 한 실행 계획이 소유한다. 복합 브러시도 이 계획 아래 두 팁·마스크·합성을 조정한다.

| 논리 모델 | 보존할 정보 |
| --- | --- |
| BrushAsset | 불변 내용 해시, 원본 브러시 파라미터, 팁·종이·안료 자산, 출처 |
| BrushInstance | 선택 자산과 현재 크기·색·불투명도·대칭 override |
| DeviceCalibration | 장치별 필압 교정과 좌표 변환; 작품의 반응 곡선과 분리 |
| BrushCapabilities | 제작/live/settle/commit/export, tilt·pickup·wet·mask·height, 실제 실행 프로필 |
| CompiledBrush | 고정된 공급자·구현 해시, 색 공간, 시간 정책, 자원 예산 |
| BrushSession | accepted 입력, 되돌릴 수 있는 predicted 표시, 난수·reservoir·dirty 영역 |
| StrokeReceipt | 입력/체크포인트, 자산·구현·시드·바탕·시간·override·결과 타일 참조 |
| CanvasMaterialState | 안료 농도, 두께, coverage, 수분, 바인더, 종이 상태 |

수명주기는 `resolve → validate → prepare → begin → append → present → settle → commit → dispose`이며 cancel과 오류를 처음부터 구현한다. Worker 응답에는 세션과 입력 순번을 붙인다. 예측 입력은 정본 안료·난수·이력을 변경하지 않는다. 엔진 고유 설정은 손실 많은 공통 슬라이더로 평탄화하지 않고 타입이 있는 전용 설정으로 보존한다.

공통 접촉 계산기는 기존 재료 경로의 기준이다. Perfect Freehand/Google Ink는 선형상·메시와 입력 모델, Hokusai/libmypaint는 원본 자연매체 동작, CanvasKit/Vello는 기하·표면 표시, Spectral/open-km/Mixbox/ColorMix는 선택된 혼색·광학, p5.brush는 절차 생성 역할을 맡는다. 렌더러 교체와 재료 물리 교체를 같은 동작으로 취급하지 않는다.

## 5. 제작 UX

`원본 편집 / 복제 후 편집 / 특성을 참고해 새로 만들기 / 다른 엔진으로 변환`을 별도 동작으로 제공한다. 정확한 원본을 못 여는 경우 유사 레시피를 원본인 것처럼 열지 않는다. 원고에서 잘라온 바탕·종이·기존 도막 상태를 쓰는 샌드박스를 제공하고 적용 전에는 실제 문서를 변경하지 않는다.
시험지는 마른/젖은 종이, 밝은/어두운 바탕, 투명 레이어, 같은 기록 입력의 A/B 비교, 실제 크기/확대 비교를 지원한다. 현재 크기·색·불투명도 등의 유효값과 원본 기본값을 함께 보여준다. 프리셋을 조정해 저사양용으로 만드는 것은 명시적 복제다.
기본 편집은 선 굵기·질감·번짐·혼색·반응처럼 결과 중심으로, 전문 편집은 곡선·팁·재료·합성·지원 정보를 단계적으로 연다. 미연결 기능은 기능 이름과 필요한 조건을 표시하고 활성 선택은 막는다. 썸네일도 실제 런타임으로 기록 입력을 재생해 만든다.

첫 수직 슬라이스는 옆면 흑연·갈필·치즐 마커·문서 해칭·다색 필버트·수관의 6종을 후보로 삼는다. 새로운 독립 엔진을 여섯 개 추가하는 대신 방향 접촉, reservoir, 문서 위상, 공간 분포라는 재사용 가능한 기반을 검증한다. 실제 수채/도막 효과는 필요한 상태 저장이 완료된 뒤 승격한다.

## 8. 광학과 성능의 선행 조건

KM은 분광 흡수·산란의 광학 모델이다. RGB 복원은 실측 안료가 아니며 반사율만으로 독립 K와 S, 실제 두께 단위를 정할 수 없다. 안료 자산에는 파장·K/S·단위·광원·관측자·바인더·바탕·출처·보정 불확실성이 필요하다. 학습/보정에 쓰지 않은 혼합·도막 측정으로 검증한다.
층 합성은 농도 혼합과 다르다. 바탕을 포함한 광학 결과를 같은 바탕에 다시 alpha 합성하지 않는다. coverage와 실제 두께를 따로 보존한다. 수분 이동·건조·모세관 흐름·침전·광택은 별도 모델이다.
2048×2048×38×float32는 한 필드만 608MiB다. 전체 분광 화면 버퍼보다 활성 타일·안료 기저·오차를 검증한 LUT를 사용한다. 입력 이벤트마다 GPU→CPU readback을 수행하지 않고 변경 타일과 고정된 시뮬레이션 순서로 처리한다.

## 9. 승격 검사와 목표 예산

아래 값은 **제안 목표**이며 측정 결과나 출시 보장이 아니다. 저사양·태블릿·데스크톱 프로필에서 실측 후 확정한다.

| 영역 | 통과 조건/제안 목표 |
| --- | --- |
| 동일 엔진 일관성 | 고정 입력·상태·시간의 제작/원고/재열기 결과와 내부 상태 비교 |
| 공통 펜 응답 | 메인 스레드 입력·계획 p95 2ms 이내를 초기 목표로 계측 |
| 프레임 | 60Hz 16.7ms, 120Hz 8.3ms 전체 예산 안에서 GPU·UI·commit 분리 |
| 다른 backend | 형상·경계·알파 및 지각 색차 별도 검사; ΔE00 평균1/p95 2는 초기 후보일 뿐 |
| 긴 획 | accepted 입력을 버리거나 획 끝을 자르지 않음; 분할·체크포인트 사용 |
| 자원 | 프로필별 resident 한도, 종료 후 누수 없음, 예열/최초 실행 구분 |
| 실패 | 취소·컨텍스트 손실·용량 부족·동시 편집 시 기존 정상 문서 보존 |
| 다양성 | 크기·농도를 맞춘 비교, 사용자 과제·블라인드 구분 평가, 조절값 실제 영향 |

테스트 입력은 짧은 점, 작은 글씨, 급회전, 자교차, 펜 멈춤, 1만 샘플 긴 획, 낮은 alpha, 극단 필압, 대칭, 페이지 이동, 타일 경계, 색 바탕과 동일 seed를 포함한다. 입력→표시 지연은 실제 장치 관측과 앱 계측을 구분한다. 합성 점수나 단순 CPU 시간으로 물리 품질·펜 latency를 주장하지 않는다.

## 10. 자산·문서·협업

가져온 원본 설정은 exact/summary/native/inert/unsupported로 구분하고 조용히 손실 매핑하지 않는다. 브러시와 의존 팁·종이·안료를 해시로 고정한다. 임의 코드 실행 대신 검증된 선언 형식을 사용하고 압축 크기·자산 수·메모리 한도를 둔다. 협업 참여자가 엔진을 지원하지 못하면 정본 결과 타일은 볼 수 있어야 하며 로컬 근사로 기록을 덮어쓰면 안 된다. 재현용 구버전 데이터는 내부에 남기고 UI에 세대를 선택하게 하지 않는다.

## 11. 구현 순서

| 단계 | 범위 | 다음 단계의 필수 조건 |
| --- | --- | --- |
| P0 정체성 | 표시 정리, 정확한 편집/참고 생성 분리, 사용 가능성 표 | 브러시 열기만으로 엔진이 달라지지 않음 |
| P1 공통 Session | 제작/썸네일/원고의 입력과 실행 계약, effective override | 기존 브러시의 전 생명주기 회귀 통과 |
| P2 네이티브 연결 | 원본 설정을 유지하는 native live/settle/commit | 후처리 변환이 아닌 실제 그리기 경로 통과 |
| P3 재사용 표현 기반 | 방향 접촉·reservoir·문서 위상·공간 분포와 6개 대표 과제 | 개성·수정 가능성·성능이 비교로 증명됨 |
| P4 재료 상태 | pickup·KM 도막·농도·두께·바탕 및 Undo | 재열기 후 동일한 재료 상호작용 |
| P5 고급 물리·타일 | 수채 운반·강모·높이, GPU dirty tiles | 저사양·장시간·자원 손실 복구 기준 통과 |
| P6 생태계 | 공유·가져오기·협업·출력·인증 | 엔진/자산 부재를 포함한 이식성 검사 |

일정은 단계별 산출물과 통과 기준으로 정하고 한 번에 전체 엔진을 갈아엎지 않는다. 측정 기준을 완화하거나 작업 중 다른 엔진으로 몰래 바꾸는 최적화는 금지한다.

## 12. 이번 변경의 범위와 검증

구현한 것은 UI의 세대/패키지 숫자 제거, 재료 중심 레시피 그룹, 원본 편집이 아닌 유사 레시피 시작임을 밝히는 안내다. 원본 매핑을 공통 자산으로 교체하거나 새 런타임·64개 브러시를 구현하지 않았다. 내부 ID·스키마·시드·버전·기존 렌더 계산은 유지한다. 숫자가 포함된 라이선스 명칭도 변경하지 않는다.
관련 회귀 테스트 471개/29파일이 통과했다. 최초 실행에서는 이전 버전 문자열의 노출을 요구하던 UI 테스트 1개가 실패하여 새 표시 계약으로 갱신했다. 내부 공급자 ID와 버전이 그대로인지 검사하는 테스트 3개를 추가하고 필수 CI에도 등록했다. 프로덕션 빌드·원격 CI·main 병합·운영 배포는 별도로 확인해야 한다.
