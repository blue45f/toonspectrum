# ADR 0001 — V11 그린필드 트리를 기존 toonspectrum 모노레포의 *-v11 네임스페이스에 배치

## 상태

승인 (2026-08-07) · **동일자 개정 — 아래 "개정(스트랭글러 통합)" 절이 결정 3·4항과 신규 앱 계획을 대체한다**

## 개정 (2026-08-07, 스트랭글러 통합)

제품 오너 결정: **새 모노레포/신규 앱 셸을 만들지 않고 기존 스튜디오 코드를 V11 아키텍처로 재개발한다.** 이에 따라:

1. `apps/studio-web-v11`·`apps/asset-market-v11` 등 **신규 앱은 만들지 않는다.** V11의 실행 표면은 기존 `/studio` 앱이다.
2. V11 엔진 계층(`packages/*-v11`, `crates/*-v11`, `tests/`)은 유지하며, **기존 스튜디오가 이를 점진 도입**한다(스트랭글러 패턴). 도입 순서는 (a) 기존 23개 브러시 백엔드의 ProviderDescriptor 역주입, (b) HybridExecutionPlanner 섀도 패리티 관측, (c) 계약 검증 후 실경로 위임.
3. import 방향은 **legacy → V11 단방향 허용**(기존 스튜디오가 V11 패키지를 소비), V11 패키지가 legacy 코드를 import하는 것은 계속 금지한다.
4. "기존 트리 무수정" 원칙은 폐기하되, 다른 세션이 편집 중인 파일(StudioPage.tsx 및 4개 Studio* 컴포넌트)과 원문 고정 boundary 계약은 침범하지 않는 최소 침습 통합만 허용한다.
5. LEGACY_DATA_MIGRATION=FALSE는 무의미해진다 — 기존 문서 데이터는 그대로 기존 스튜디오의 데이터이며 폐기 대상이 아니다. Phase 8 "컷오버"는 "legacy 라우트 제거"가 아니라 "엔진 선택 경로의 V11 플래너 위임 완료"로 재정의한다.

## 맥락

V11 최종 아키텍처는 "기존 코드를 점진적으로 교체하지 않는다. 새 V11 monorepo를 만들고 기존 내부 데이터는 최종 컷오버 때 폐기한다"고 규정한다(§12). 마스터 프롬프트도 `GREENFIELD_REWRITE=TRUE`, `LEGACY_DATA_MIGRATION=FALSE`를 유일한 권위 원칙으로 선언하고, `/apps/studio-web-v11`부터 `/crates/format-gateway-v11`까지의 `*-v11` 접미사 트리와 `/tests/corpus`·`/tests/benchmarks`·`/tests/fault-injection`을 명시한다.

한편 §12는 "기존 화면·기능·테스트는 요구사항과 비교 자료로 읽을 수 있다"고 하여 기존 자산의 읽기 접근을 요구한다. 물리적으로 분리된 신규 저장소를 만들면 이 read-only 참고, 기존 CI·검증 스크립트 재사용, docs/의 벤치마크·경쟁 분석 축적물 참조가 모두 끊긴다.

## 결정

1. V11 트리를 **별도 저장소가 아니라 기존 toonspectrum 모노레포 안**에 만든다.
2. 모든 V11 산출물은 `*-v11` 접미사 네임스페이스를 사용한다: `apps/studio-web-v11`, `apps/asset-market-v11`, `apps/benchmark-lab-v11`, `packages/ui-v11`, `packages/command-registry-v11`, `packages/provider-catalog-v11`, `crates/*-v11`, `tests/corpus`, `tests/benchmarks`, `tests/fault-injection`.
3. 기존 앱·패키지(비-v11 트리)는 **read-only 참고**다. V11 작업이 기존 트리를 수정하지 않으며, V11 코드가 기존 런타임 코드를 import하지 않는다. 문서·테스트·화면은 요구사항 비교 자료로만 읽는다.
4. **기존 내부 데이터 마이그레이션은 하지 않는다.** 기존 스토어·API·데이터는 Phase 8 컷오버 때 명시적 파괴 플래그로 폐기한다(§13 Phase 8). 외부 창작 포맷 호환은 FormatGateway에서 최대화한다.

## 근거

- 논리적 그린필드(신규 네임스페이스·의존 차단)로 §12의 "전면 재작성" 요구를 충족하면서, 같은 저장소이므로 "기존 화면·기능·테스트를 요구사항과 비교 자료로" 읽는 요구도 마찰 없이 충족한다.
- 기존 verify 게이트·CI·corpus 축적(docs/의 벤치마크 문서군)을 V11 벤치마크 하니스가 직접 참조할 수 있다.
- `*-v11` 접미사는 마스터 프롬프트의 모노레포 명세와 문자 그대로 일치하며, 컷오버 시 legacy 트리 제거 대상을 기계적으로 식별하게 한다.
- 별도 저장소 대안은 참고 접근성·CI 재사용을 잃는 비용 대비 격리 이득이 없다 — 격리는 워크스페이스 경계와 import 금지 린트로 달성 가능하다.

## 결과

- V11 워크스페이스 설정(pnpm workspace·Cargo workspace)이 `*-v11` 경로만 포함하도록 구성된다.
- 기존 트리 수정을 차단하는 경계(리뷰 규칙 + 린트/CI 검사)가 필요하다.
- V11→legacy import 금지 규칙이 필요하다(역방향 참조도 금지 — legacy는 V11을 모른다).
- 컷오버 전까지 두 트리가 공존하므로 저장소 크기·CI 시간이 일시적으로 증가한다.
- 기존 데이터를 읽는 마이그레이터를 만들지 않으므로 그 개발·검증 비용이 0이 된다. 대신 사용자 자산 연속성은 외부 포맷 import(SUT/SUTG/ABR/MYB/KPP/Krita bundle)가 담당한다.

## 재검토 조건

- 모노레포 CI 시간·저장소 크기가 V11 개발 속도를 실질적으로 저해할 때(분리 저장소 재검토).
- Phase 8 컷오버 완료로 legacy 트리가 제거되어 `*-v11` 접미사 자체가 무의미해질 때(네임스페이스 정리 재검토).
- 기존 내부 데이터의 보존 요구가 제품 결정으로 새로 발생할 때(LEGACY_DATA_MIGRATION 원칙 자체의 상위 재결정 필요).
