# ToonSpectrum 웹툰 직군 분업·협업 작업공간 v5

## 1. 목적

웹툰 제작을 일반적인 상태 칸반이 아니라 **직군별 책임, 선행 산출물, 검수자, 정본 인수인계가 연결된 제작 시스템**으로 운영한다.

이번 구현은 다음 문제를 해결한다.

- 같은 작업 목록을 보더라도 스토리, 작화, PD·편집자가 필요한 정보의 우선순위가 다르다.
- 콘티가 잠기기 전에 선화·배경이 시작되거나, 산출물 없이 검수·승인으로 넘어가면 재작업 비용이 커진다.
- 외주 인력은 `vendor`라는 계약 관계만으로 분류하면 실제 배경·채색 공정의 병목에서 사라진다.
- 담당자와 검수자가 한 목록에 섞이면 책임과 승인 경계가 불명확해진다.
- 회차 흐름, 인력 공백, 검수 대기, 마감 위험을 서로 다른 화면에서 찾아야 하면 PD의 판단 속도가 느려진다.

## 2. 제품 벤치마크

특정 서비스의 외형을 복제하지 않고 여러 제작·검수 도구의 공통 운영 패턴을 웹툰 도메인에 맞게 재구성했다.

| 참고 서비스 | 확인한 패턴 | ToonSpectrum 적용 |
| --- | --- | --- |
| Clip Studio Paint Teamwork | 다중 페이지 작품을 클라우드에서 공유하고 페이지 단위로 협업 | 프로젝트 정본을 공유하되 회차·공정 범위별 작업과 인수인계를 분리 |
| Toon Boom Producer | 제작 단계, 작업, 에셋, 장면, 팀, 진행률과 보고서를 한 생산 문맥에서 연결 | 직군 작업 셀, 회차 필터, 잔여 공수, 차단·검수·인력 공백 지표 |
| Kitsu | Task Type 기반 워크플로, 부서별 큐, 제출 버전, supervisor review, 보고서 필터 | 직군별 queue, 담당자·검수자 분리, 단계 게이트, 역할·범위 기반 자동 배치 |
| Frame.io | 버전 스택, 정확한 위치의 의견, 내부·외부 의견 경계, 승인 흐름 | revision 입력·산출물 연결, 검수 상태, 내부 역할과 외부 파트너의 정보 경계 |

## 3. 직군 모델

기존 `ProductionRoleType`과 `RoleAssignment`를 유지하면서 운영 화면에서 다음 10개 작업 셀로 정규화한다.

1. 스토리·각색
2. 콘티·연출
3. 캐릭터·선화
4. 배경·3D
5. 밑색·채색
6. 식자·효과음
7. 번역·현지화
8. 편집·통합 검수
9. 제작·게시 운영
10. 권리·크레딧

각 작업 셀은 다음을 가진다.

- 주 담당 역할
- 검수 가능 역할
- 공정명 alias
- 기본 완료 기준
- 배정된 assignment와 리드
- 열린 작업, 진행 작업, 검수 대기, 차단, 완료 수
- 마감 초과·임박 수
- 예상 잔여 공수
- 충원 상태와 건강 상태

### 공정 우선 분류

작업 셀 분류는 역할보다 `processKey`를 먼저 본다.

예를 들어 외부 협력사가 배경 작업을 맡아도 `vendor` 역할 때문에 제작 운영 셀로 들어가지 않고 `background` 공정에 따라 배경·3D 셀에 들어간다. 공정명이 모호할 때만 담당자·검수자 역할의 가중치로 보완한다.

## 4. 표준 웹툰 제작 파이프라인

기본 공정은 다음 순서를 사용한다.

```text
대본 잠금
  → 콘티·연출
    ├→ 캐릭터·선화 ─┐
    └→ 배경·3D ─────┤
                     └→ 채색·이펙트
                       → 식자·효과음
                         → 통합 교정
                           → 게시 패키지
```

권리·크레딧 검수는 제작 중 병렬로 진행하지만 게시 패키지의 필수 입력이다.

이 구조는 선화와 배경의 병렬 생산성을 유지하면서 채색부터 다시 하나의 통합 정본으로 합류하도록 한다.

## 5. 단계 게이트

모든 작업은 단순 상태값 외에 다음 조건을 계산한다.
- 미완료 또는 유실된 선행 작업
- 고정되지 않은 입력 revision
- 미배정 주 담당자
- 미배정 검수자
- 연결되지 않은 산출물
- 마감 초과 또는 72시간 이내 마감

차단 조건과 주의 조건을 분리한다.

- **차단**: 선행 작업, 입력 정본, 주 담당자가 없으면 작업 시작·검수 요청을 막는다.
- **주의**: 검수자, 산출물, 마감 위험을 명시하고 해당 단계에 필요한 전환만 제한한다.
- **검수 요청**: 작업 중이며 차단 조건이 없고 검수자·산출물이 있을 때만 가능하다.
- **승인**: 검수 상태이며 검수자·산출물이 있을 때만 가능하다.

UI는 비활성 버튼만 표시하지 않고 차단 이유를 문장으로 제공한다. 서버 명령에서도 기존 `transitionProductionTask` 규칙을 다시 적용하므로 화면 우회로 잘못된 전환을 만들 수 없다.

## 6. 작업공간 정보 구조

### 직군 보드

- 왼쪽: 전체 직군, 현재 역할 관점, 개별 작업 셀
- 가운데: 준비·대기, 제작 중, 검수·승인, 승인·완료의 4개 queue
- 오른쪽: 선택 작업의 입력·산출물·선행 작업·공수·완료 기준·담당자·검수자·상태 전환
- 상단: 회차 필터, 작업·담당자 검색, 활성 셀·차단·검수·인력 공백·잔여 공수 지표

### 공정 흐름

- 8개 표준 단계를 가로 파이프라인으로 표시
- 단계별 작업 수, 차단 수, 완료율, 선행 직군 표시
- 선화와 배경의 병렬 분기 및 채색 합류를 시각적으로 표현
- 단계 카드 또는 작업 카드를 선택하면 같은 상세 패널을 사용

### 팀 구성

- 직군별 리드 유무와 현재·예정 assignment 표시
- 열린 작업과 예상 공수를 함께 표시
- 열린 작업이 있는데 담당자가 없으면 미충원 위험으로 강조
- 역할 배정과 실제 기여·권리·보상 기록은 기존 원장처럼 분리

### 역할 관점

스토리 작가, 작화팀, PD·편집자의 역할 관점은 정본 데이터를 복제하지 않고 기본적으로 강조할 작업 셀만 바꾼다.

- 스토리: 스토리, 콘티, 식자, 편집
- 작화: 콘티, 선화, 배경, 채색, 식자
- PD·편집: 편집, 제작, 권리, 현지화

사용자는 언제든 전체 직군 또는 특정 셀로 전환할 수 있다.

## 7. 담당자·검수자 배정

작업 상세에서 주 담당자와 주 검수자를 바로 변경할 수 있다.

추천 후보는 다음 조건을 모두 만족해야 한다.

1. 해당 작업 셀의 담당 또는 검수 역할
2. 활성 또는 온보딩 assignment
3. 작업의 `ScopeRef`를 포함하는 assignment 범위
4. assignment 종료 시점 이전

미배정 작업 자동 배치는 같은 규칙으로 가장 적합한 리드·시작일 순 후보를 선택한다. 자동 배치는 현재 필터에 보이는 미배정 작업에만 적용하며, 저장은 기존 `upsert-task` 명령을 사용한다.

시작일이 미래인 assignment는 현재 담당·검수 후보에서 제외한다. 팀 구성 화면에는 **충원 예정**으로 따로 보여 주어 예정 인력을 현재 가용 인력으로 오인하지 않도록 한다. 검수 승인도 선행 작업, 입력 정본, 현재 가용 담당자 조건을 모두 통과해야 가능하다.

## 8. 데이터 호환성
이번 변경은 신규 DB 테이블이나 API 계약을 추가하지 않는다.

기존 모델을 그대로 조합한다.

- `RoleAssignment`: 직군, 범위, 리드, 활성 기간
- `ProductionTask`: 담당자, 검수자, 입력 revision, 산출물, 선행 작업, 마감, 공수, 완료 기준
- `Deliverable`: 공정 결과물과 승인 제출본
- `ReviewPolicy`: lane별 검수 자격과 게시 차단
- `ScopeRef`: 프로젝트·회차·장면·컷 범위
- `upsert-task`: 담당·검수·상태 변경 저장

따라서 기존 프로젝트도 공정명과 역할 배정이 있으면 자동으로 작업 셀에 투영된다. 분류할 수 없는 작업은 별도 `unclassifiedTaskIds`로 남겨 조용히 잘못 분류하지 않는다.

## 9. 샘플 스튜디오 프로젝트

샘플 프로젝트를 실제 분업 흐름으로 확장했다.

- 콘티 작가
- 선화 작가
- 배경 외주 스튜디오
- 채색 작가
- 식자 담당
- 편집자
- 권리 검수
- 스토리 리드, 작화 리드, 프로듀서

12화에는 콘티 → 선화/배경 → 채색 → 식자 → 권리 검수/통합 교정 → 게시 패키지의 작업과 산출물을 연결했다. 13화 대본 작업도 병행해 여러 회차가 서로 다른 공정에 놓이는 실제 연재 상황을 표현한다.

## 10. 접근성·반응형 원칙

- 보기 전환과 직군 선택에 `aria-pressed` 제공
- 검색, 회차, 담당자, 검수자 필드에 명시적 접근 가능한 이름 제공
- 상태·위험을 색상뿐 아니라 텍스트 라벨과 아이콘으로 함께 표시
- 좁은 화면에서는 패널을 세로로 쌓고, 칸반과 파이프라인은 안전한 가로 스크롤 제공
- 작업 선택은 키보드로 접근 가능한 버튼 사용
- 읽기 전용 사용자는 배정과 상태 전환 컨트롤을 비활성화

## 12. 후속 확장 경계

이번 단계는 작업 분배와 승인 가능한 정본 흐름을 고도화한다. 다음 확장은 현재 모델을 우회하지 않고 다음 순서로 진행한다.

1. 작업 템플릿: 장르·스튜디오별 직군 구성과 완료 기준 preset
2. 용량 계획: assignment별 주간 가용 시간, 휴가, 외주 SLA
3. 검수 inbox: 역할별 검수 대기와 응답 기한 알림
4. 산출물 diff: PSD·Studio 문서·이미지 revision의 시각 비교
5. 외부 게스트 포털: 공개 범위를 제한한 납품·피드백 공간
6. 실시간 presence: 같은 회차·작업·검수본을 보는 사용자 표시
7. 자동화 규칙: 승인 시 다음 작업 준비, 마감 위험 escalation, 게시 전 권리 gate

실시간 공동 편집과 바이너리 파일 잠금은 별도 동기화 계층이 필요하지만, 현재의 `ScopeRef`, revision, 역할, 산출물, 검수 정책을 권한과 정본 기준으로 계속 사용한다.
