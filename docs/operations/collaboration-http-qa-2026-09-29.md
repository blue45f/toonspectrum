# 협업 일반 계정·HTTP·PostgreSQL 검증

상태: **current** · 기준일: **2026-09-29**

## 수정한 문제

1. 일반 테스트 계정 가입 도구가 필수 `x-toonstudio-csrf` 증명을 보내지 않아 403으로 거절됐다.
   브라우저와 같은 공유 계약 상수를 사용한다. CSRF 검사나 출처 검사는 해제하지 않는다.
   가입 실패는 계정 역할·HTTP 상태만 진단하고 비밀번호·서버 응답 본문을 출력하지 않는다.
2. 프로젝트 생성의 재전송 영수증을 현재 작품 소유권보다 먼저 조회해, 소유권을 잃은 계정이
   과거 요청을 재전송하면 이전 비공개 응답을 다시 받을 수 있었다.
   영수증 조회 전에 작품 행을 잠그고 현재 소유자를 다시 확인한다.
3. 같은 프로젝트 생성 요청이 동시에 들어오면 둘 다 영수증 없음으로 판단해 한쪽이 409로 실패했다.
   작품 잠금 이후에 영수증을 읽어 같은 요청은 최초 성공 결과를 반환하고 중복 생성하지 않는다.

수정 전 실제 HTTP·PostgreSQL 테스트에서 두 저장소 문제를 재현했다.
각각 `[201, 409]` 대신 `[201, 201]`, 소유권 회수 뒤 `201` 대신 `403`을 요구하는 회귀 검사다.

## 검증 경계

새 `production-auth-http.integration.test.ts`는 일반 가입 API로 계정 3개를 생성한다.
비밀번호 해시, 이메일 인증 토큰 발급·일회성 소비, 로그인, HttpOnly 쿠키, 세션 검증,
CSRF, Nest 컨트롤러, 협업 서비스, 트랜잭션 저장소는 실제 구현을 실행한다.
관리자 계정이나 `demo-*` 사용자, 임의의 평문 사용자 헤더로 인증을 대체하지 않는다.

외부 이메일 공급자의 전송 호출만 격리된 메모리 수신함으로 대체한다.
따라서 실제 이메일 발송·운영 계정 생성 성공의 증거는 아니다.
작품과 작품별 ACL은 격리 DB fixture로 준비하며, 팀 가입과 프로젝트 명령은 HTTP로 실행한다.
테스트 계정의 서비스 역할은 모두 `user`이고 작품별 소유자·편집자·열람자 권한을 별도로 검증한다.

## HTTP 시나리오

| 영역 | 검증 |
| --- | --- |
| 가입·인증 | 미인증 로그인 차단, 인증 후 일반 계정 로그인, 인증 토큰 재사용 차단 |
| 세션·CSRF | 쿠키 복원, 캐시 금지, 평문 사용자 ID 위조 차단, 잘못된 출처·증명 차단 |
| 팀 | 생성 재전송, 대상 이메일 확인, 초대 수락 재전송, 초대 회수·재발행 |
| 팀 권한 | 비관리자 승격·이름 변경 차단, 마지막 소유자 제거 차단, 동시 변경 충돌 |
| 작품 연결 | 팀 가입만으로 원고 접근 권한이 생기지 않음, 프로젝트 생성 동시 재전송 |
| 소유권 회수 | 이전 생성 영수증으로 원고를 다시 읽지 못함 |
| 제작 공정 | 관리자만 설정, 순환 공정·낡은 설정 버전 거절 |
| 작업 보드 | 편집자/열람자 분리, 입력 버전 고정, 동시 진행 한도, 승인 없는 완료 차단 |
| 저장 신뢰성 | 요청 ID 재사용·내용 변경 충돌, 동시 저장 하나만 성공, 회수된 권한 재검사 |
| 검수·로그아웃 | 다른 검수자 역할 사칭 차단, 승인자 결정 저장, 다른 탭의 오래된 쿠키 무효화 |

## 재현

파괴 가능한 로컬 PostgreSQL 테스트 DB만 지정한다. 테스트가 고유 스키마를 생성·정리한다.
운영 연결 문자열이나 운영 환경변수를 복사하지 않는다.

```sh
TEST_DATABASE_URL='<격리된 로컬 PostgreSQL 테스트 URL>' pnpm exec vitest run \
  apps/api/src/modules/production-collaboration/production-auth-http.integration.test.ts --maxWorkers=1
node --test scripts/collaboration-qa-accounts.test.mjs
pnpm harness:verify
```

표준 PostgreSQL 통합 검사 목록에도 신규 HTTP 검증을 추가했다.
테스트 계정·인증 토큰은 출력하거나 영구 fixture로 저장하지 않고, 종료 시 스키마와 세션을 정리한다.

## 운영 가입 확인 결과와 제한

사용자 소유 메일함의 별칭 주소로 가입 정보를 준비했다. 자격정보 파일은 gitignore·파일 권한 600으로 보호했다.
CSRF 수정 후 정상 가입 요청이 `503`으로 실패해 운영 계정 생성·메일 인증·로그인 성공은 확인하지 못했다.
`2026-09-28T15:09:43Z`의 요청 `req_2212`와 검증용 빈 요청 `req_2219`를 Render 로그에서도 확인했다.
새 운영 배포가 live가 된 뒤의 `2026-09-28T15:32:36Z` 재확인도 `503`(`req_216`)이었다.
빈 요청 재확인은 가입 데이터를 만들지 않는다. 로그는 실패 상태만 보여 정확한 내부 원인은 확정하지 않는다.

운영 가입이 정상화되어야 실제 운영 계정의 초대·공동 편집·검수까지 종단 간 검증할 수 있다.
위 가입·검증 과정에서 이메일 인증을 건너뛰거나 관리자 권한을 주입하지 않았으며, 운영 설정·DB·배포를 변경하지 않았다.
PR 병합은 운영 배포 승인이 아니다. 이 API 수정의 운영 반영에는 별도 배포 절차가 필요하다.

브라우저 회귀 검사는 기존 두 검증기를 사용한다. UI 세션 검사는 합성 HTTP 응답,
작업 보드 검사는 합성 프로젝트를 사용한다. 신규 실제 HTTP·DB 검증과 범위를 혼동하지 않는다.

## 최종 로컬 검증과 후속 DB 판정

관련 회귀는 **59개 파일, 378개 테스트**를 통과했다. 실제 HTTP·PostgreSQL 20개가 포함된다.
가입 도구의 Node 테스트 6개와 기존 브라우저 검사 26개도 통과했다. 브라우저의 미처리 오류는 없었다.
병렬 회귀에서 lazy 검수 패널 대기 1건이 실패해, 동적 모듈과 React 반영 완료를 기다리도록 검증 시점을 정정했다.
기존 고정 review·revision·artifact 검증을 그대로 유지했으며 수정 후 해당 파일 8개도 다시 통과했다.

2026-09-29 사용자가 메인 병합과 필요한 DB 후속 작업을 요청했다.
현재 운영 권위인 Supabase에서 협업 프로젝트·팀 스키마와 runtime 역할은 확인했지만,
`admin_member_test_accounts`는 없고 관리형 원장은 0091까지 적용되어 있었다.
새 DB 생성은 필요하지 않다. 관련 기능에 독립적으로 필요한 0097만 적용 대상으로 판정했다.
0092~0096은 이번 후속 작업에 포함하지 않는다. 기존 데이터 이관·초기화·계정 권한 변경도 하지 않는다.
0097은 별도 폐기 가능한 로컬 PostgreSQL에서 재실행·RLS·제약·감사 실패 롤백 등 15검사를 재통과했다.
운영 적용 결과는 병합된 PR의 후속 실행 기록에 남기며, 병합 전 판정을 적용 완료로 해석하지 않는다.
